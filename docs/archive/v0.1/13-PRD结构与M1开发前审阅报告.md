# PRD 结构与 M1 开发前审阅报告

## 一、审阅目的与范围

本文档用于整理当前有声书产品收入评估与年度目标系统的产品定位、业务边界、开发里程碑、文档一致性和 M1 开发前置条件，为后续逐章冻结需求及正式开发提供依据。

本次重点阅读了 `README.md`、`01-总体PRD-v0.1.md`、`02-冲突检查与覆盖记录.md`、`11-待定项与数据验证计划.md` 和 `12-里程碑与验收总表.md`，并补充阅读了 `00`、`03` 至 `10` 的专项文档，以核对各项规则的上下文和相互引用关系。

本报告不补充新的业务规则。凡原文明确标记为需要通过真实账单、运营案例或历史回测确定的阈值、算法和数值，本文继续保持待定。

## 二、对系统定位的理解

本系统是面向有声书运营负责人和一线运营的内部分析与决策支持平台。它以财务系统导出的真实实销账单为事实基础，通过数据清洗、渠道统一、作品归并、主数据补全、收入预测、产品评级和年度目标管理，为运营提供可追溯的分析依据。

系统的核心业务链路可以概括为：实销账单治理形成可信数据底座；以标准作品为核心建立作品、作者、渠道、分类和标签主数据；分别完成老品和新品收入评估；利用历史回测、运营案例和不合理反馈持续校准算法；在老品预测稳定后，将预测结果转化为下一自然年度实销目标，并持续跟踪实际完成情况。

系统不替代财务系统。财务系统仍然是金额事实的最终权威来源，本系统只负责对账单进行重复识别、渠道统一、作品归并和分析处理。系统也不负责未上线项目的排期、制作、签约和资源审批，不自动输出“是否开发”或“是否继续运营”等机械结论。最终业务决策仍由运营根据评级、预测、风险、建议和判断依据作出。

## 三、业务边界

系统将已经产生实销的标准作品定义为老品。老品进入老品库后，可以基于历史收入、版权期限、产品状态、分类标签和其他有效信息进行生命周期识别、剩余版权期收入预测、评级和运营建议生成。

上线前评估对象统一称为选题，保存在选题库。未产生实销的选题与老品库和年度目标无关，也不会提前创建待收入的老品记录。选题产生首笔实销后，由运营补充作品 ID，系统查找已有标准作品并建立正式关联。一个选题只能正式关联一部标准作品，一部标准作品也只能选择一个选题作为新品回测基准。

标准作品使用数字主体 ID 作为运营可见的唯一业务 ID。例如 `12345` 和 `Y12345` 都归属于标准作品 `12345`。纯数字 ID 表示有声版权，`Y` 前缀 ID 表示有声成品。两种业务形态分别统计收入，但文档要求它们共享标准作品层的综合评级、预测、运营建议、版权期限和产品状态。

年度目标只允许纳入制定目标时已经产生实销、已经进入老品库并具有有效正式老品评估的作品。未上线选题不进入年度目标。目标年度内后来产生收入的目标外作品会自动进入执行表，其目标值为零，实际收入计入公司实销完成率，但不修改原实销目标，也不进入原目标作品的预计实销完成。

正式评估结果不得直接覆盖。重新评估必须生成新记录，旧结果保留为历史版本或标记为已失效，同时保留输入快照、技术版本和失效原因。基础数据错误、账单撤销、作品归并变化或规则变化导致结果失效时，系统自动发起重新评估。

## 四、六个开发里程碑

### 4.1 M1 数据基础

M1 的目标是建立可信、可追溯、可撤销、可恢复的数据底座。范围包括账单上传和解析、数据质量检查、问题退回、本地修正、正式导入、批次管理、渠道统一、历史分册归并、标准作品生成、基础信息补全、分类和标签管理，以及支撑这些流程所必需的任务、备份、恢复和一致性检查能力。

M1 完成后，全量真实账单应能够被处理并严格对账，关键异常必须能够阻断正式导入，批次导入和撤销不能破坏数据一致性，标准作品和主要主数据对象必须完整，备份与恢复流程必须通过验证。

### 4.2 M2 老品评估

M2 基于 M1 的真实实销数据和作品主数据，对已经产生实销的标准作品进行历史收入分析、生命周期识别、剩余版权期收入预测、评级、风险和运营建议生成，并使用历史时间截断方式进行回测。

M2 的关键完成条件是能够批量评估全量有效老品，预测算法具有历史回测证据，正式结果具备版本、失效和自动重评闭环，页面和导出的统计口径保持一致。

### 4.3 M3 新品评估

M3 面向上线前选题，支持 Word、PPT、PDF 材料解析和手动创建。系统在运营确认结构化信息后查询外部数据，选择精准对标作品，在符合条件时进行作者作品排位，输出首年和五年收入预测、新品评级、支撑因素、限制因素和风险。

选题产生实销后，系统通过作品 ID 与标准作品建立一对一正式关联，并默认使用上线前最后一次正式新品评估作为首年、三年和五年回测基准。

### 4.4 M4 算法校准与修复

M4 建立从运营案例和不合理反馈到算法修复的完整闭环。运营案例经过结构化确认后形成候选规则，Codex 结合多个案例和历史账单整理正式规则、代码或提示词修改。修改通过代表案例和验收用例后启用，并对受影响作品自动重新评估。

这一阶段还包括反馈聚合、问题组、Codex 问题包、影响范围识别、批量重评、修复报告和回滚。正式结果和历史结果仍必须保持可追溯。

### 4.5 M5 辅助能力

M5 补全完整任务中心、通知、邮件、Excel 导出、可复制文字报告、历史评估对比和监控能力。部分基础任务能力必须从 M1 开始随核心流程同步建设，M5 负责将其补充为完整、统一的辅助能力。

M5 完成后，长任务应能在页面关闭后继续运行，任务可以追踪、取消和按失败类型重试，重要结果不会遗漏通知，导出与页面口径保持一致。

### 4.6 M6 年度目标

M6 将有效老品评估转化为下一自然年度实销目标，并提供月度拆分、实际实销、预计实销完成、完成率、汇总图表、筛选、下钻、版本和年度复盘。

年度目标必须只使用有效正式老品评估。目标外收入进入实际实销和公司完成率，但不回溯修改正式目标，也不进入原目标作品的预计实销完成。年度结束后目标锁定业务修改，但允许修正明确的数据错误。

M1 至 M4 是核心首期建设内容，M5 和 M6 后续开发，但系统正式投入使用前必须完成 M1 至 M6 的全部功能、测试、真实数据验证、运营验收、文档和缺陷处理。

## 五、文档之间需要澄清的问题

### 5.1 任务状态不能覆盖所有任务类型

当前文档统一列出的任务状态为“排队中、评估中、复核中、已完成、已取消、任务失败”。这套状态适合评估任务，但不能准确覆盖账单导入、数据导出、备份、恢复和邮件发送等任务。账单导入任务不存在“评估中”和“复核中”，因此需要区分所有任务共享的通用状态与不同任务类型自己的业务阶段。

### 5.2 “评估异常”的对象层级不清

总体 PRD 将“评估异常”定义为本次未形成正式结果，但算法校准文档又将其与“当前有效、历史版本、已失效”并列保存。需要明确评估异常究竟是一次评估尝试的状态、正式评估记录的状态，还是作品层的提醒。否则开发时容易把失败尝试错误地当作正式评估版本。

### 5.3 标准作品上线时间存在歧义

上线时间被定义为第一笔实销入账年月，但一个标准作品可能同时具有纯数字和 `Y` 前缀两种业务形态，而两种形态可能在不同月份首次产生收入。需要明确标准作品上线时间是否取所有业务形态中的最早月份，是否同时保留每种业务形态自己的首次实销月份，以及年度目标中的“新品实销”按标准作品还是业务形态判断。

### 5.4 统一版权期限需要真实业务验证

文档规定有声版权和有声成品共享标准作品层的版权期限。如果真实业务中两种业务形态可能具有不同授权期限，当前规则将无法完整表达实际权利状态。开发前需要使用真实数据确认这一约束是否始终成立。如果不成立，应重新进行业务确认，不能由开发自行假设处理方式。

### 5.5 M1 分类完成条件与待验证事项存在循环依赖

M1 要求完成分类和标签主数据，但分类体系和标签库的具体内容又要在全量账单分析后最终确认。因此应明确区分两类要求：开发前冻结分类层级、版本、兜底和修改机制；真实数据分析后再冻结具体分类树和标签值。同时需要明确哪部分属于 M1 开发前置条件，哪部分属于 M1 验收条件。

### 5.6 原始账单字段的保存范围不明确

账单输入同时包含实销金额、参与分成实销金额和不参与分成实销金额，但正式统计只使用实销金额。文档尚未明确后两个字段是在正式导入后继续保留但不参与统计、仅用于校验，还是正式入库时不保存。该问题会直接影响数据追溯和对账能力，需要在 M1 开发前明确。

### 5.7 不合理反馈与正式结果有效性的关系不清

运营标记为不合理的评估结果仍可进入汇总和导出，但文档没有明确“不合理”标记是否影响当前有效结果身份、年度目标使用资格和自动重评优先级。该标记应作为独立业务属性还是触发结果失效，需要进一步确认。

## 六、重复规则和长期维护风险

当前文档中，同一规则经常同时出现在总体 PRD、冲突覆盖记录和专项文档。例如选题与老品的边界、标准作品 ID、评估版本和失效、年度目标作品范围、AI 不降级、测试使用真实数据副本以及 M1 至 M6 的范围，都存在多处重复描述。

这些描述目前基本一致，但长期维护时容易只修改其中一处，导致不同文档重新出现分歧。尤其是将冲突覆盖记录永久设为最高优先级，会要求开发者在实施一条规则前同时查询总体 PRD、专项文档和覆盖记录，增加遗漏风险。

更稳定的方式是让每条正式规则只有一个权威定义位置。总体 PRD 只保留摘要并链接到专项文档，里程碑文档只引用需求编号，冲突覆盖记录在结论确认后转为历史决策记录，同时把最终结论更新到权威专项文档中。

## 七、需要改写为可验收语义的技术约束

### 7.1 大型账单的整批事务

如果“整批事务写入”被解释为整个大型文件始终处于一个数据库长事务中，可能引起长时间锁定、事务日志膨胀和失败恢复困难。需求应强调业务原子性：数据可以分块进入临时区域，在全部校验通过后统一切换批次状态，外部不能看到部分正式导入结果。具体数据库实现不应由 PRD 预先限定为一个长事务。

### 7.2 批量重评逐个发布与整批回滚

文档同时要求成功结果逐个发布和支持整批回滚。逐个发布后，普通数据库事务已经无法覆盖整个批次，因此需要明确整批回滚是基于批次版本执行补偿恢复，并定义每部作品应恢复到哪个历史版本。

### 7.3 数据库迁移自动回滚

代码、配置和规则通常可以自动切换回旧版本，但破坏性数据库迁移不一定能够安全执行逆向回滚。技术要求应增加数据库迁移兼容原则、关键操作前恢复点和无法自动逆向迁移时的恢复流程，避免形成无法保证实现的绝对承诺。

### 7.4 完整真实数据副本

测试环境使用完整真实数据副本在技术上可实现，但文档目前缺少最低访问控制、创建权限、保留期限、销毁方式、凭证隔离和操作记录要求。即使第一阶段不建设复杂权限系统，也必须在 M1 前冻结真实数据副本的最低安全边界。

### 7.5 指定 AI 模型不可用时不降级

不自动切换到较弱模型的原则是明确的，但还需要定义最大等待方式、任务取消、通知升级和模型恢复后的继续执行语义。否则任务可能无限停留，任务中心也无法向运营解释当前状态。

## 八、仍需补充定义的数据对象、字段和状态

### 8.1 M1 数据对象

M1 需要进一步定义导入文件与导入批次之间的关系、临时解析记录、数据问题记录、人工处理决定、清洗规则及规则版本、批次撤销记录、恢复点引用、受影响作品集合、财务原始 ID 与标准作品映射、历史分册 ID 映射、渠道别名冲突记录、主数据变更记录、分类体系版本、分类节点状态、标签库版本、标签状态、作者别名和作者归并记录。

这些对象是否独立保存、如何关联以及哪些信息必须可追溯，需要在需求层明确。本文不涉及数据库表设计。

### 8.2 M1 关键字段语义

需要补充定义的字段语义包括：年月格式和月份边界、财务 ID 规范化规则、前导零处理、`Y` 前缀大小写和非法格式处理、文件指纹算法、重复文件判定范围、原始行唯一定位方式、金额精度、币种和舍入方式、零金额和负金额记录标记、标准作品名称来源、每种业务形态的首次实销月份、批次覆盖月份表示方式、数据截止月份计算方式，以及文件删除时间和删除失败处理。

### 8.3 后续里程碑数据对象

后续还需要定义评估输入快照及版本、AI 模型和提示词版本、规则版本、外部数据版本、评估尝试与正式评估结果的关系、作品级待重新评估提醒、不合理反馈标记、新品和老品回测记录、年度目标版本、目标作品快照、滚动预计版本、问题组、问题包、修复批次和影响范围快照。

### 8.4 状态体系

不建议所有对象共享一套状态。至少需要分别定义文件状态、导入批次状态、数据问题状态、通用任务状态、任务业务阶段、正式评估状态、作品重评提醒、产品状态、选题流程状态、年度目标状态、规则版本状态和问题组状态。

状态定义应包含状态含义、进入条件、退出条件、允许的操作、失败处理和是否允许恢复。具体阈值仍按真实数据验证计划保持待定。

## 九、当前文档结构是否适合长期维护

“总体 PRD 加专项文档”的总体方向适合 Codex 阅读。它具有明确入口，单个文件长度可控，Codex 可以根据任务只读取相关领域文档，而不必每次加载全部业务背景。

但当前结构更适合作为 v0.1 汇总版和逐章冻结阶段的材料，不适合作为长期唯一规范。主要原因是同一规则多处重复、覆盖记录长期具有最高优先级、缺少稳定需求编号、待定项没有反向关联受影响需求、里程碑验收没有映射到具体规则、单个文档缺少独立状态信息，并且所有文件按序号平铺，后续扩展时容易继续形成大型综合文档。

Codex 更适合读取“单一事实来源、明确入口、单向引用、稳定需求编号”的文档体系。每条详细规则应只有一个权威定义位置，其他文档通过链接和需求编号引用，不重复抄写正文。

## 十一、M1 开发前必须冻结的需求

### 11.1 M1 范围和依赖

必须明确 M1 的完整范围，以及任务、通知、备份、恢复、监控和权限能力中哪些是 M1 流程不可缺少的基础设施，哪些可以留到 M5 补全。不能因为完整任务中心属于 M5，就使 M1 的大型账单任务缺少后台运行、进度、失败和恢复能力。

### 11.2 账单字段和金额口径

必须冻结财务账单字段定义、数据类型、年月格式、金额精度、币种、舍入方式和正式统计口径。需要明确参与分成实销金额和不参与分成实销金额是否保留，以及它们在对账和追溯中的作用。

### 11.3 文件、批次和原始记录

必须冻结导入文件、导入批次、原始记录、临时解析记录、问题记录和正式收入记录之间的业务关系。还需要明确文件指纹和重复上传判定语义、原始行定位方式、批次覆盖月份、数据截止月份，以及正式导入后各类文件和元数据的保留与删除规则。

### 11.4 数据问题和对账

必须冻结重复记录、疑似重复、合法冲抵、渠道冲突、作品冲突和分册冲突的处理流程，并区分阻断问题和非阻断问题。需要明确人工逐项确认、本地修改、重新上传的业务流程，以及原始金额、确认删除金额和正式入库金额之间的对账公式。

重复识别的扩展异常模式可以继续通过真实账单总结，但规则版本和人工处理结果如何沉淀必须提前确定。

### 11.5 正式导入和撤销

必须冻结整批原子导入的业务语义、失败时的外部可见结果、幂等要求和恢复方式。还要明确批次撤销的操作资格、操作记录、恢复点、受影响作品识别、评估失效触发和重新导入方式。

### 11.6 渠道和作品 ID

必须冻结统一渠道对象、渠道别名、渠道更名和别名冲突处理规则。必须明确标准作品 ID 的规范化方式、纯数字和 `Y` 前缀业务形态识别、前导零和非法格式处理，以及历史分册归并、主 ID 选择、隐藏映射和冲突阻断规则。

### 11.7 标准作品和业务形态

必须明确哪些字段属于标准作品，哪些字段属于业务形态。标准作品上线时间与业务形态首次实销时间的关系必须冻结。两种业务形态共享版权期限和产品状态的规则，需要在真实业务数据中得到确认后再作为正式约束。

### 11.8 基础信息、作者、分类和标签

必须冻结基础信息补全模板、必填项、上传校验和错误反馈方式。作者与作者别名的最小业务规则也应明确。

分类和标签可以暂不冻结最终具体值，但必须先冻结分类层级结构、分类路径唯一性、兜底节点原则、版本管理、修改权限和变更影响机制。标签需要冻结辅助内容标签与特殊属性标签的边界、固定库机制、版本和修改流程。

### 11.9 产品状态

必须冻结已上架、疑似下架、已下架和重新上架四种状态的业务含义、允许的转换和人工确认边界。疑似下架观察周期、基本无收入金额、连续无收入月数和预测归零条件继续保持待真实数据验证，不应在开发前猜测具体数值。

### 11.10 任务、权限和环境安全

必须冻结 M1 所需的通用任务状态、导入业务阶段、任务取消、失败分类、重试、幂等和恢复语义。指定 AI 模型不可用时的等待、通知和取消规则也需要在涉及 AI 的任务开发前明确。

即使第一阶段不建设复杂权限，也必须冻结最低访问控制，包括谁可以上传、确认、正式导入、撤销、归并和创建真实数据副本。测试环境必须明确禁止回写正式环境，并隔离邮件、凭证和任务。

### 11.11 备份、恢复和一致性检查

必须冻结每日备份、关键操作恢复点、备份异地保存、恢复验证和恢复后健康检查的要求。M1 至少需要覆盖批次金额、收入记录、ID 映射、渠道映射、标准作品关联和撤销后数据一致性。

### 11.12 M1 验收标准

必须在开发前准备可执行的验收标准，包括全量账单处理、严格对账、重复文件识别、关键问题阻断、整批原子导入、撤销和恢复、分册归并、渠道更名、基础信息补全、真实数据性能测试和无阻断缺陷。

验收标准应映射到稳定需求编号和具体测试用例，避免仅使用“数据主对象完整”或“备份恢复通过”等无法直接判定的概括性描述。

## 十二、可以继续保持待定的内容

重复识别的扩展异常模式、最终分类树、最终标签库、疑似下架阈值、文件大小上限、正式性能指标、并发数、重试次数、任务记录保留期限、主要渠道默认展示数量、“其他”渠道合并规则，以及所有评级、生命周期、预测区间、外部数据、通知和月度拆分阈值，都可以继续保持待定。

这些内容不应在代码中写死未经验证的具体数值，但开发前必须为它们提供明确的配置位置、版本机制、验证计划和启用流程。

## 十三、总体结论

当前 PRD 已经明确了系统的核心业务链路、主要边界和六个里程碑，足以继续进行需求冻结工作，但尚不适合直接进入稳定的 M1 开发。

M1 开始前，应优先冻结数据对象语义、ID 规则、时间与金额口径、文件和批次关系、问题处理流程、撤销恢复机制、状态体系和最低安全边界。具体评级门槛、生命周期阈值、预测算法、性能数值和其他标记为真实数据分析后确定的内容，应继续保留为待定，不作主观推测。
