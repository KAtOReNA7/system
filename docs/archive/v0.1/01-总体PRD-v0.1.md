# 01. 总体 PRD v0.1

## 1. 项目背景

公司已有多年有声书实销账单，但账单存在重复、渠道更名、分册拆分、负数冲抵、结算延迟和基础信息缺失等问题。运营需要一套以真实账单为基础、能够持续回测和校准的产品分析系统，用于：

- 判断老品未来收入、生命周期和当前价值；
- 评估新品选题的首年与五年收入；
- 建立统一评级体系；
- 发现算法偏差并通过 Codex 修复；
- 在预测稳定后形成年度实销目标。

## 2. 目标

### 2.1 业务目标

- 形成可信、可追溯的实销数据底座。
- 使老品预测和新品预测具备历史回测证据。
- 用 S/A/B/C/D/E（允许 S+）建立产品价值分层。
- 支持运营按需发起单个或批量评估。
- 通过案例、反馈、规则和自动重评形成算法闭环。
- 将老品预测结果转化为下一自然年度实销目标。

### 2.2 非目标

- 不替代财务系统。
- 不管理尚未产生实销的项目排期、制作流程或签约流程。
- 不为每个分析维度建立独立管理后台。
- 不以成本优先选择低能力模型，第一阶段优先保证算法正确。
- 不在首期开发复杂权限体系。
- 不自动切换到较弱 AI 模型。

## 3. 用户与权限

### 3.1 第一阶段用户

- 运营负责人；
- 一线运营；
- Codex 作为开发和技术维护工具。

### 3.2 第一阶段权限原则

- 先完成核心功能和算法稳定性，不建设复杂角色权限。
- 运营可查看全部作品并执行大多数操作。
- 敏感操作保留技术记录，但第一阶段不建设重型审计后台。
- 系统稳定后再收紧分类、归并、撤销和删除等权限。

## 4. 核心术语

### 4.1 标准作品

以数字主体 ID 为唯一业务 ID。例如 `12345` 与 `Y12345` 均属于标准作品 `12345`。

### 4.2 业务形态

- 纯数字 ID：有声版权，即文字版权授权后由非我方开发的有声产品。
- `Y` 开头 ID：有声成品，即我方开发的有声成品。

两种形态分别统计收入，但原作级综合评级、预测和建议统一输出。

### 4.3 上线时间

统一定义为第一笔实销入账年月。

### 4.4 首年

从第一笔实销入账月份起连续 12 个月。三年和五年分别为连续 36 个月和 60 个月。

### 4.5 实销金额

账单统计只使用“实销金额”字段。参与分成实销、不参与分成实销不进入正式统计口径。

### 4.6 新品与老品

- 新品：选题库中的上线前评估对象。
- 老品：已经产生实销账单并进入老品库的标准作品。
- 新品产生实销后，运营补充作品 ID，系统与已有老品建立关联并开始回测。

## 5. 产品范围

### 5.1 M1 数据基础

账单上传、校验、退回、本地修正、正式导入、渠道统一、分册归并、标准作品、基础信息补全、分类和标签。

### 5.2 M2 老品评估

历史收入分析、生命周期、剩余版权期预测、评级、运营建议、风险、参考作品和历史回测。

### 5.3 M3 新品评估

选题材料解析、信息确认、外部查询、精准对标、作者作品排位、首年和五年收入预测、新品评级、选题与老品关联、首年/三年/五年回测。

### 5.4 M4 算法校准与修复

运营案例、候选规则、正式规则、不合理反馈、问题组、Codex 问题包、自动重评、代表案例验证、批量回滚。

### 5.5 M5 辅助能力

批量任务、任务中心、通知和邮件、Excel 与文字报告、历史评估对比。基础任务能力随 M1-M4 同步建设。

### 5.6 M6 年度目标

下一自然年度实销目标、月度拆分、实际实销、预计实销完成、汇总图表、下钻和年度复盘。

## 6. 总体业务流程

### 6.1 数据准备

账单上传 → 临时解析 → 全量校验 → 生成问题文件和清洗报告 → 本地修正 → 重新上传 → 整批事务导入 → 导出基础信息补全表 → 运营补全 → 分类标签确认 → 老品可评估。

### 6.2 老品评估

运营从老品库发起评估 → 系统读取历史实销和基础信息 → 生命周期识别 → 多算法预测和回测选择 → 生成剩余版权期预测、评级、建议与风险 → AI复核与必要裁决 → 发布正式结果。

### 6.3 新品评估

上传 Word/PPT/PDF 或手动新建 → AI分块解析 → 左右对照确认 → 删除原始文件 → 外部查询 → 系统与运营对标 → 作者排位（符合条件时） → 首年和五年预测 → 评级和风险 → 发布正式结果。

### 6.4 选题转老品

作品产生实销 → 运营在选题库补充一个作品 ID → 系统查找已有老品并确认 → 建立一对一正式关联 → 默认使用上线前最后一次正式新品评估为回测基准 → 首年/三年/五年回测。

### 6.5 算法修复

运营标记不合理 → AI聚合相似反馈 → 问题组 → Codex问题包 → Codex修复规则/代码/提示词 → 代表案例验收 → 新版本启用 → 受影响作品自动重评 → 修复报告与回滚。

### 6.6 年度目标

第四季度提示创建下一年度目标 → 读取最新账单和有效老品评估 → 默认选择下一年度预测收入大于0的作品 → 生成自然年度实销目标和月度拆分 → 发布目标快照 → 新账单更新实际实销和原目标作品预计实销完成 → 年度结束锁定并复盘。

## 7. 核心数据对象

- 账单导入批次；
- 原始收入记录；
- 统一渠道与渠道别名；
- 标准作品；
- 业务形态；
- 作者；
- 主分类；
- 辅助标签；
- 特殊属性标签；
- 选题记录；
- 新品评估记录；
- 老品评估记录；
- 外部数据版本；
- 运营案例；
- 候选规则与正式规则版本；
- 不合理反馈、问题组和Codex问题包；
- 任务记录；
- 年度目标和目标版本；
- 备份与恢复点。

## 8. 全局评估原则

- 同一输入重复评估应基本稳定，允许的波动范围通过回测确定。
- 正式评估采用高性能模型，不考虑成本优先。
- 正式评估需要 AI 初判、自动复核，并在明显分歧时裁决。
- 评估结果不直接覆盖，重新评估生成新记录。
- 当前有效结果唯一；旧结果转历史版本。
- 基础数据错误导致原结果“已失效”，自动发起重评。
- 评估异常表示本次未形成正式结果；已失效表示曾有效但后来不可继续使用。

## 9. 评级体系

- 等级：S、A、B、C、D、E，允许 S+。
- 新品和老品同级含义不完全等价。
- 评级以收入预测基础等级为起点，结合其他因素修正。
- 外部事件最多上调两级。
- S+需负责人或运营确认。
- E为下架级；D边界需通过历史账单确定。
- 不展示具体评分。
- 新品不设置资源投入等级；老品保留三档资源投入等级。

## 10. 页面与导航原则

### 10.1 一级导航

产品分析优先，数据准备和模型校准放入设置或辅助区域。建议导航：

- 首页；
- 老品库；
- 选题库；
- 年度目标；
- 任务与通知；
- 数据与设置。

### 10.2 页面设计原则

- 需求文档确定信息架构、字段、口径和交互边界。
- 正式视觉方案由产品设计插件或专业工具重新设计。
- Codex负责实现，不直接以默认WebUI作为最终设计。
- 高密度列表优先，详情页按概览、收入/预测、依据、基础信息、历史记录组织。

## 11. 非功能要求

- 大型账单后台异步、分块处理，最终整批事务提交。
- 页面关闭后任务继续执行。
- 同一作品重复任务自动合并或删除后发起。
- 系统动态控制批量评估并发。
- 指定AI模型不可用时不降级，等待恢复并重试。
- 正式数据库与开发测试环境隔离。
- 开发测试环境使用完整真实数据副本。
- 每日备份 + 关键操作恢复点。
- 核心数据一致性自动检查。
- 严重故障通知中心 + 邮件，普通异常仅通知中心。

## 12. 版本与发布

- AI模型、提示词、规则和配置纳入Git版本控制。
- Codex修改需经过自动测试、代表案例、真实数据验收和运营试用。
- 部署失败时按影响范围自动回滚，并生成Codex故障材料。
- 一个里程碑只有在功能、自动测试、真实数据、运营验收、文档和缺陷状态全部合格后才算完成。

## 13. 正式投入使用条件

- M1-M6全部完成；
- 全部模块通过内部试用；
- 老品与新品算法达到验收标准；
- 年度目标可用；
- 无阻断性缺陷；
- 完成接近全量的真实数据迁移演练；
- 备份、恢复、监控和发布流程通过验证。

## 14. 待数据验证事项

评级门槛、生命周期分类与阈值、预测算法、预测区间、月度拆分、下架和归零条件、渠道展示规则、性能指标、外部数据有效期、异常通知阈值等，统一在真实账单、运营案例和回测后确定。
