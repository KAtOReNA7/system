# M1 物理数据模型 v0.4（PostgreSQL 16 原型验证收口版）

> 状态：**PROTOTYPE VALIDATED — NOT A FORMAL MIGRATION**  
> 日期：2026-06-21  
> 数据库：PostgreSQL 16.14  
> 基线：`M1-物理数据模型-v0.3.md`  
> 边界：本文冻结经隔离实例验证后新增的物理不变量；不生成正式 Flyway 迁移，不装载真实数据，不新增 PENDING-DATA 业务规则。

## 1. v0.4 结论

v0.4 保留 v0.3 的 47 张 M1 业务表、1 张 `system_state` 控制表、`NUMERIC(32,18)`、完整映射快照、基础信息作用域快照和作品 ID 解析规则。表数量仍为 48，不新增物理表。

隔离验证发现并修正四类实现缺口：

1. `ready_for_bill_activation` 必须与 `operational` 一样，要求 mapping、basic_info、classification、tag 各恰好一个 active 版本；
2. 仅保护版本头状态不足以保证快照不可变，版本子表也必须受数据库触发器保护；
3. `ready` 批次和 active 批次事实必须冻结，不能在严格对账或激活后继续追加或改写；
4. 新分类 release、新标签 release 与引用它们的基础信息版本必须在同一事务切换，不能先后暴露不一致组合。

v0.3 的字段、主外键、唯一约束、保留策略和 REQ/AT 归属继续有效；与本文冲突时以 v0.4 为准。

## 2. system_state 冻结语义

| 状态 | mapping active | basic_info active | classification active | tag active |
|---|---:|---:|---:|---:|
| `schema_initialized` | 允许 0 | 允许 0 | 允许 0 | 允许 0 |
| `master_data_initializing` | 允许 0 | 允许 0 | 允许 0 | 允许 0 |
| `ready_for_bill_activation` | 恰好 1 | 恰好 1 | 恰好 1 | 恰好 1 |
| `operational` | 恰好 1 | 恰好 1 | 恰好 1 | 恰好 1 |

“最多一个 active”由四个部分唯一索引保证；“ready/operational 至少一个 active”由读取 `system_state` 的 deferred constraint trigger 在提交时保证。

`master_data_initializing -> ready_for_bill_activation` 只能调用受控初始化函数。该函数在一个事务内：

1. 取得全局版本切换 advisory transaction lock；
2. `FOR UPDATE` 锁定 `system_state`；
3. 创建或校验 bootstrap mapping、basic_info、classification、tag；
4. 将四类对象各激活一个；
5. 将状态切换到 ready；
6. 由延迟约束在提交时复核四个 active 计数。

首批账单激活在一个短事务内退休 bootstrap mapping、激活真实 mapping、激活首批批次并切换到 operational。基础信息、分类和标签 bootstrap 版本可以继续 active。

## 3. 快照冻结边界

### 3.1 映射快照

以下子表仅允许在所属 `mapping_version.status='building'` 时插入、更新或删除：

- `channel_alias`；
- `raw_work_id_mapping`；
- `historical_volume_mapping`；
- `income_projection`；
- `mapping_version_work_metric`；
- `mapping_version_work_form_metric`。

`mapping_version` 从 `building` 进入 `validated` 后，版本头、映射行、投影和指标全部冻结。`validated -> active -> retired` 只能由受控函数完成。这样可以保证严格对账使用的 checksum、行数和实际投影不会在切换前被替换。

### 3.2 基础信息快照

以下子表仅允许在所属 `basic_info_version.status='building'` 时变更：

- `basic_info_version_work`；
- `work_classification_assignment`；
- `work_tag_assignment`。

基础信息版本进入 `validated` 后，版本头及上述子表冻结。未进入 active 基础信息版本的新 `standard_work` 继续由缺口视图识别，不阻断账单批次激活。

### 3.3 分类与标签 release

`classification_node` 仅允许在 `classification_release.status='draft'` 时变更；`tag` 仅允许在 `tag_release.status='draft'` 时变更。active 或 retired release 不得覆盖修改。

## 4. 批次与收入事实冻结

`income_fact` 的新增只允许发生在所属批次为 `draft` 或 `validating` 时。`UPDATE`、`DELETE` 始终由不可变触发器拒绝。

批次进入 `ready` 后，严格对账字段、checksum、行数和金额冻结；`ready -> active` 以及 `active -> revoked` 只能由受控函数执行。这样避免 active mapping 已按旧事实集合验证，而同一 active 批次随后又新增事实。

撤销仍只改变批次状态和当前 mapping 快照，不删除或修改 `income_fact`。

## 5. 分类、标签与基础信息原子切换

`switch_basic_info_version` 的 v0.4 语义：

1. 只允许在 `operational` 执行；
2. 候选基础信息版本必须为 `validated`；
3. 候选引用的 classification/tag release 必须为当前 active 或 draft；
4. 若引用新 draft release，先在同一事务退休旧 active release，再激活新 release；
5. 退休旧 active 基础信息版本并激活候选版本；
6. deferred lifecycle trigger 在提交时检查 classification、tag、basic_info、mapping 仍各恰好一个 active；
7. 任一步失败，旧组合保持可见，新组合整体回滚。

具体分类值、标签值和必需标签仍为 PENDING-DATA，不写入原型常量。

## 6. 作品 ID 与映射不变量

- `12345` 与 `Y12345` 是不同完整原始作品 ID；
- 两者都派生标准作品 ID `12345`；
- 业务形态分别为 `audio_copyright`、`audio_product`；
- 授权分类不参与业务形态推导；
- 非法 ID 解析为无效结果，不猜测修正；
- `raw_work_id_mapping` 与 `historical_volume_mapping` 在同一版本内跨表互斥；
- `historical_volume_mapping` 在同一版本内按完整历史原始 ID 唯一，唯一键不含 `business_form`；
- deferred 互斥触发器锁定所属 `mapping_version` 行，防止并发插入绕过跨表检查。

## 7. 权限与 SECURITY DEFINER

所有切换函数固定 `search_path=pg_catalog,m1`，并撤销 PUBLIC 执行权。应用角色不具备版本头直接切换权限。

状态保护不能只信任调用方可自行设置的自定义 GUC。原型要求同时满足：

- 当前执行身份为 `migration_owner`；
- 受控 SECURITY DEFINER 函数在当前事务设置内部切换上下文。

`application_rw` 不得直接修改 `income_fact` 或 active 版本；`application_ro` 仅查询正式视图；`background_worker` 可构建候选但不能激活；`backup_operator` 无业务写权限。

## 8. 原子切换锁定顺序

批次激活、撤销、纯映射切换、基础信息/分类/标签切换统一采用：

1. `pg_advisory_xact_lock` 获取全局版本切换锁；
2. `system_state FOR UPDATE`；
3. 目标批次或目标版本行 `FOR UPDATE`；
4. 执行覆盖范围与严格对账检查；
5. 先退休旧 active，再激活候选；
6. 更新批次和 lifecycle 状态；
7. 写入幂等影响事件；
8. 提交时运行延迟约束。

读视图只按 active 版本和 active 批次读取，因此不会看到同一事务中的中间状态。并发切换在 advisory lock 上串行化；lock timeout 的事务不产生半完成状态。

## 9. 隔离验证结论

PostgreSQL 16.14 隔离实例实际创建 48 张表、5 个正式视图、21 个函数、32 个用户触发器、84 个外键和 117 个索引。76 项测试全部通过，包括生命周期、deferred trigger、不可变快照、权限、并发超时和 192,899 行合成数据基线。

性能数据仅是当前硬件上的观测基线，不是上线阈值。详见《M1-非正式迁移原型验证报告-v0.1.md》。

## 10. 进入正式迁移整理的门禁

技术上允许把本原型整理成正式 Flyway SQL-only 候选迁移，但不得直接复制为正式历史。整理前必须：

1. 把原型中的测试角色和本地实例参数改为环境配置；
2. 对每个 SECURITY DEFINER 函数做逐项权限审查；
3. 将原型大文件拆为正式命名规范要求的业务原子迁移；
4. 在全新隔离库再次执行相同不变量与并发测试；
5. 继续保持真实数据迁移门禁，未解决运营确认结果不得装载。
