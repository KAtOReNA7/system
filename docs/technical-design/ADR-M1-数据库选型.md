| 项目 | 内容 |

## 1. 背景

M1 当前已完成真实账单和数字版权台账分析，关键事实如下：

- 现有收入事实为 `192,899` 行，后续会随账单持续增长；
- 金额必须保留 Excel 底层完整精度，权威金额和对账计算不得使用 `float` / `double`；
- 需要后台异步任务、批次原子切换、版本化收入投影、恢复点、撤销、受控重新导入和幂等处理；
- 初期用户和并发有限，但未来可能出现多人同时使用、运营上传、开发/测试/正式环境并行；
- 正式数据库必须与开发、测试环境隔离；
- 需要可靠事务、唯一约束、检查约束、索引、备份和恢复；
- 当前尚无既定数据库技术栈。

## 2. 决策

M1 正式数据库推荐使用 **PostgreSQL 16+**。

开发、测试和正式环境均使用 PostgreSQL，但必须使用独立实例或独立数据库，并使用独立凭据、备份策略和访问控制。不得使用 SQLite 作为正式数据库。

金额字段统一使用 `NUMERIC(32,18)` 作为 M1 物理模型的权威金额类型。该精度可覆盖当前观测到的最大整数位 9 位、最大小数位 18 位和当前最大批次合计 `253610173.052208979970873801`，并为未来增长预留 14 位整数空间。

月份字段使用 PostgreSQL `date` 表示自然月首日，并通过检查约束保证日期为当月 1 日。这样可以避免 `YYYY-MM` 文本排序、时区和日期范围歧义。

## 3. 候选比较

### 3.1 PostgreSQL

优势：

- 事务、MVCC、行级锁和约束能力成熟，适合批次原子切换、版本指针切换和并发运营操作；
- `NUMERIC(32,18)` 可作为权威金额类型，满足完整精确十进制要求；
- 支持唯一约束、部分唯一索引、检查约束、外键、延迟约束和表达式索引，可把核心数据一致性下沉到数据库；
- `SELECT ... FOR UPDATE SKIP LOCKED`、事务锁和 advisory lock 可支撑后台任务队列和幂等任务领取；
- 支持可靠备份恢复、PITR、逻辑备份、只读副本和未来横向读扩展；
- 支持分区，但当前 19 万行规模不要求立即分区，可等真实增长和查询压力确认后再引入。

代价：

- 运维复杂度高于 SQLite，需要实例管理、备份、权限、监控和环境隔离；
- `NUMERIC(32,18)` 的存储和聚合成本高于整数或浮点，需要在索引和聚合缓存设计中控制使用范围；
- 需要明确连接池、事务边界和迁移管理流程。

结论：满足 M1 的原子性、版本化、恢复和未来多人使用边界，是唯一推荐方案。

### 3.2 SQLite

优势：

- 部署简单，适合单机原型和本地只读分析；
- 初期 19 万行数据规模本身不是 SQLite 的容量问题；
- 无需独立数据库服务。

放弃原因：

- 写并发能力和长事务控制不适合运营上传、后台任务、批次切换和多人使用叠加场景；
- 约束、锁、备份、权限隔离和线上恢复能力不如 PostgreSQL；
- 开发/测试/正式环境隔离容易退化为文件复制和路径约定，不符合正式数据管理要求；
- 后续从 SQLite 迁移到 PostgreSQL 会增加金额、日期、约束、并发语义的二次校准成本。

结论：可用于一次性本地分析脚本的临时缓存，不作为正式数据库。

### 3.3 MySQL / MariaDB

优势：

- 成熟关系型数据库，支持事务、索引、外键、`DECIMAL` 和常规备份；
- 部署经验普遍，生态完善。

放弃原因：

- PostgreSQL 在检查约束、部分索引、表达式索引、复杂事务约束、版本化数据建模和后台任务领取方面更直接；
- M1 对“不可变事实 + 当前有效版本 + 受控重建 + 严格对账”的一致性约束较多，PostgreSQL 的约束表达能力更适合把关键不变量放到数据库层；
- 当前没有既定 MySQL 技术栈约束，因此没有为了兼容历史系统而选择 MySQL 的理由。

结论：可作为备选企业栈，但本项目无必要优先采用。

## 4. 部署影响

- 至少划分 `dev`、`test`、`prod` 三套数据库或实例，禁止共用正式库；
- 正式库账号按角色拆分：应用读写账号、只读分析账号、迁移账号、备份账号；
- 后台任务和批次切换需要统一使用数据库事务，不允许在应用内用文件锁替代；
- 大文件暂存、问题确认和版本构建可以在较长后台任务中执行，但“正式可见版本切换”必须是短事务；
- 初期无需表分区，保留按月份分区的演进边界。

## 5. 备份与恢复影响

- 正式库必须启用定期全量备份和 WAL/PITR 能力；
- 每次正式批次激活、撤销、映射版本激活、基础信息整批应用前，必须创建逻辑恢复点记录；
- 恢复点不是简单复制业务表，而是记录可恢复到的数据库备份位置、业务版本号、批次号和校验摘要；
- 文件原件的留存与删除按 PRD 规则执行，数据库中保留文件元数据、指纹、批次金额和清洗报告。

## 6. 未来扩展边界

短期不做：

- 不因当前 19 万行数据立即进行收入事实表分区；
- 不引入数据仓库、OLAP 引擎或搜索引擎；
- 不把后台任务队列外置到消息队列，除非任务吞吐或可靠性要求超过 PostgreSQL 行锁队列能力；
- 不为 M2/M4 预先建立未经确认的评估、预测或自动重评规则表。

未来可扩展：

- 当收入事实达到千万级并出现明确月份裁剪查询压力时，按 `bill_month` 引入分区；
- 当报表读取压力影响写入时，引入只读副本或独立分析库；
- 当后台任务吞吐明显超过数据库队列能力时，再引入专用队列。

## 7. 后续动作

1. 基于 PostgreSQL 编写 `M1-物理数据模型-v0.1.md`；
2. 在文档层完成表、约束、索引和事务边界设计；
3. 通过运营确认包和物理模型验证后，才允许进入数据库迁移设计阶段；
4. 进入迁移设计阶段仍不得自动生成迁移文件，需另行确认。
