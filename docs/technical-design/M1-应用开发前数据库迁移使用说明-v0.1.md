# M1 应用开发前数据库迁移使用说明 v0.1

状态：允许用于开发/测试空库建模；仍禁止正式数据迁移。

本文说明应用开发前如何使用正式 Flyway SQL-only 迁移目录 `db/migrations/` 建立本地开发或测试数据库结构。本文不授权导入真实账单、数字版权台账、运营确认结果，也不授权连接正式数据库。

## 1. 使用范围

允许：

- 使用 `db/migrations/` 在本地开发库或测试库创建 M1 数据库结构；
- 使用空库或纯合成数据做应用开发、接口联调和自动化测试；
- 在隔离环境中重复执行 Flyway `migrate/info/validate`。

禁止：

- 使用 `experiments/m1-flyway-candidate/migrations/` 作为应用开发迁移来源；
- 导入真实账单、数字版权台账或运营确认结果；
- 自动应用运营确认结果；
- 生成或应用正式 `mapping_version`；
- 连接或写入正式数据库；
- 修改 `db/migrations/` 下已晋升的 SQL 文件。

## 2. 数据库与角色前置要求

推荐数据库：

- PostgreSQL 16.x，当前回归验证版本为 PostgreSQL 16.14；
- 数据库会话时区使用 UTC；
- Flyway 使用 SQL-only 迁移，当前验证版本为 Flyway OSS 10.21.0。

迁移前需要预置以下数据库角色：

```sql
CREATE ROLE migration_owner LOGIN;
CREATE ROLE application_rw LOGIN;
CREATE ROLE application_ro LOGIN;
CREATE ROLE background_worker LOGIN;
CREATE ROLE backup_operator LOGIN;
```

角色用途：

| 角色 | 用途 |
| --- | --- |
| `migration_owner` | 仅用于执行 Flyway 迁移，不作为应用运行账号 |
| `application_rw` | 应用读写账号，但不得直接修改 `income_fact` 或直接切换版本 |
| `application_ro` | 只读分析/查询账号 |
| `background_worker` | 后台任务构建候选数据，不得越权激活版本 |
| `backup_operator` | 备份/恢复相关账号，无业务写权限 |

## 3. 本地空库创建示例

示例仅用于本地开发/测试环境。正式环境必须使用独立的受控数据库和凭据管理方式。

```bash
createdb -O migration_owner m1_dev
```

建议对开发/测试库设置 UTC：

```sql
ALTER DATABASE m1_dev SET TimeZone TO 'UTC';
```

## 4. Flyway 运行方式

Flyway locations 必须指向正式迁移目录：

```text
filesystem:<repo>/db/migrations
```

示例命令：

```bash
flyway \
  -url=jdbc:postgresql://127.0.0.1:<local-port>/m1_dev \
  -user=migration_owner \
  -locations=filesystem:<repo>/db/migrations \
  -schemas=flyway_history,m1 \
  -defaultSchema=flyway_history \
  -table=flyway_schema_history \
  -createSchemas=true \
  -cleanDisabled=true \
  -placeholderReplacement=false \
  migrate
```

随后执行：

```bash
flyway info
flyway validate
flyway migrate
```

第二次 `migrate` 应显示无重复执行。

## 6. 开发/测试数据边界

应用开发阶段只能使用：

- 空库；
- 手工构造的最小合成数据；
- 不含真实作品、渠道、作者、金额明细、版权日期或运营确认内容的自动化测试数据。

仍禁止使用：

- 真实账单；
- 数字版权台账；
- 运营确认 Excel 或其明细；
- 真实作品级收入明细；
- 根据运营确认结果生成的正式映射版本。

## 7. 修改迁移的规则

`db/migrations/` 已作为正式迁移目录冻结。后续不得直接修改已提交迁移文件。

如发现迁移问题，应采用：

- 新增 forward-only 修复迁移；
- 重新执行隔离库 Flyway 回归；
- 更新迁移验收报告；
- 再提交修复迁移。

不得通过修改历史 SQL、删除 Flyway history、baseline 或 repair 掩盖问题。
