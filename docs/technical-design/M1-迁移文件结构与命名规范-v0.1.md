# M1 迁移文件结构与命名规范 v0.1

| 项目 | 内容 |
|---|---|
| 状态 | MIGRATION STRUCTURE DRAFT |
| 日期 | 2026-06-21 |
| 目标工具 | Flyway SQL-only（已冻结） |
| 本轮限制 | 只设计目录、命名和规范；不创建 `db/`、`migrations/` 或正式 SQL 文件 |

## 1. 建议目录结构

以下仅为建议结构，不在本轮创建：

```text
db/
  migrations/
    0000_bootstrap/
    0010_platform/
    0020_import/
    0030_mapping/
    0040_basic_info/
    0050_recovery_audit/
    0060_functions_views/
  tests/
    ddl/
    invariants/
    concurrency/
    performance/
  fixtures/
    synthetic/
    sanitized_private/
  rollback/
    playbooks/
    pitr_drills/
```

目录含义：

| 目录 | 内容 | 是否进入正式迁移集合 |
|---|---|---|
| `db/migrations/0000_bootstrap/` | PostgreSQL 版本门禁、schema、角色、默认权限、迁移元数据、`system_state` | 是 |
| `db/migrations/0010_platform/` | 平台与基础身份表 | 是 |
| `db/migrations/0020_import/` | 文件、暂存、问题、批次、事实 | 是 |
| `db/migrations/0030_mapping/` | 映射版本、投影、指标 | 是 |
| `db/migrations/0040_basic_info/` | 基础信息版本、分类、标签、补全流程 | 是 |
| `db/migrations/0050_recovery_audit/` | 月份完整性、恢复点、撤销、影响事件、审计 | 是 |
| `db/migrations/0060_functions_views/` | 触发器、函数、视图、权限授予 | 是 |
| `db/tests/` | 隔离 PostgreSQL 验证脚本和测试说明 | 否，除非未来单独设测试迁移 |
| `db/fixtures/` | 合成或脱敏验证数据 | 否，不得包含真实账单明细 |
| `db/rollback/` | 回滚预案、PITR 演练说明 | 否，不作为自动 down migration |

## 2. 编号规则

### 2.1 目录编号

- 使用 4 位数字层级编号；
- 每层以 10 为跨度，保留中间插入空间；
- 编号不得重排；
- 已进入正式迁移集合的目录不得改名。

示例：

```text
0000_bootstrap
0010_platform
0020_import
0030_mapping
0040_basic_info
0050_recovery_audit
0060_functions_views
```

### 2.2 文件编号

推荐文件名格式：

```text
V{layer4}_{seq3}__{verb}_{object_or_group}.sql
R{layer4}_{seq3}__{object_or_group}.sql
```

含义：

| 片段 | 含义 |
|---|---|
| `V` | 一次性版本迁移，执行后不可修改 |
| `R` | 可重复执行对象，用于视图、函数等可整体替换对象；是否采用需在工具冻结时确认 |
| `{layer4}` | 4 位层级编号，例如 `0030` |
| `{seq3}` | 层内 3 位顺序号，例如 `010` |
| `{verb}` | `create`、`alter`、`add`、`grant`、`fix`、`replace` 等 |
| `{object_or_group}` | 对象名或业务原子组名，使用小写 snake_case |

示例仅用于说明，不在本轮创建：

```text
V0000_010__create_schemas_and_roles.sql
V0010_020__create_file_fingerprint_registry.sql
V0020_040__create_income_fact.sql
V0030_030__create_mapping_tables.sql
V0030_080__add_raw_work_id_cross_table_invariants.sql
V0060_040__create_batch_activation_functions.sql
R0060_090__current_read_views.sql
```

## 3. 文件粒度

### 3.1 基本原则

一个迁移文件应包含一个业务原子组，而不是机械地每张表一个文件，也不是把整层塞进一个大文件。

推荐粒度：

| 对象类型 | 文件粒度 |
|---|---|
| schema、角色、默认权限 | 一个 Layer 0 原子组 |
| 无复杂依赖的基础表 | 可按主题分组，例如平台表、身份表 |
| 权威事实表 | 单独文件或极小组，便于审查 |
| FK | 简单 FK 可随表；跨层 FK 或需拓扑后置的 FK 单独文件 |
| 唯一约束和 CHECK | 原则上随表；涉及复杂表达或 `NULLS NOT DISTINCT` 时可单独文件 |
| 索引 | 查询关键路径索引可单独文件；可延后性能测试的索引不得提前写死 |
| 触发器函数 | 函数定义单独文件，触发器绑定单独文件 |
| deferred constraint trigger | 单独文件，配套独立测试 |
| 受控切换函数 | 每类切换函数一个文件或一个紧密原子组 |
| 读取视图 | 可重复执行对象，按视图族分组 |
| 权限授予 | 每层末尾或 Layer 6 集中授予 |

### 3.2 表、FK、索引、触发器、函数和视图拆分

推荐拆分顺序：

1. 表主体；
2. 基础主键、非空、普通 CHECK；
3. 无循环风险 FK；
4. 后置 FK；
5. 普通唯一约束和部分唯一索引；
6. 查询索引；
7. 触发器函数；
8. 触发器绑定；
9. 受控函数；
10. 视图；
11. 权限。

拆分理由：

- 便于隔离 FK 依赖；
- 便于单独验证 PostgreSQL 特性；
- 避免函数引用尚未创建的表或类型；
- 便于生产失败时定位最小修复范围。

## 4. 一次性迁移与可重复执行对象

### 4.1 一次性迁移

一次性迁移用于：

- 创建表；
- 添加列；
- 添加不可重复的约束；
- 数据结构调整；
- 初始化必须存在的控制行；
- 权限初始授予。

原则：

- 已执行后不可修改；
- 修改必须追加新迁移；
- checksum 变化视为异常；
- 不允许为了“修正历史”改旧文件。

### 4.2 可重复执行对象

可重复执行对象适用于：

- 读取视图；
- 纯函数；
- 部分不保存状态的辅助函数；
- 格式化输出函数。

限制：

- 不得把数据修复逻辑放入可重复迁移；
- 不得在可重复对象中隐式改变表结构；
- 对 `SECURITY DEFINER` 函数，替换时必须重新检查 owner、`search_path` 和授权。

Flyway repeatable migration 仅用于视图、幂等可替换函数和纯辅助对象；一次性 schema 变更必须使用版本化 `V` 迁移。若采用 repeatable migration，必须在 CI 中记录对象定义 hash。

## 5. checksum 规则

推荐规则：

1. 迁移工具的 schema history checksum 是执行状态的权威；
2. Git commit hash 只作为代码版本追踪，不替代迁移 checksum；
3. 已执行迁移文件 checksum 不得变化；
4. 若发现已执行文件内容错误：
   - 不修改旧文件；
   - 追加 `fix` 或 `replace` 迁移；
   - 在验收清单中记录原因；
5. 只有未进入任何共享环境的本地草稿迁移可重写。

## 6. 修复迁移命名

修复迁移使用新的版本号，不复用旧编号。

格式：

```text
V{layer4}_{seq3}__fix_{object}_{issue}.sql
V{layer4}_{seq3}__replace_{object}_{reason}.sql
V{layer4}_{seq3}__add_{object}_{missing_invariant}.sql
```

示例仅用于说明：

```text
V0030_911__fix_historical_raw_work_id_uniqueness.sql
V0060_912__replace_batch_activation_function_lock_order.sql
V0040_913__add_basic_info_gap_view_missing_new_work.sql
```

`900-999` 号段建议保留给同层修复迁移，但不得依赖该号段绕过正常审查。

## 7. 开发、测试、正式环境规则

### 7.1 同一迁移集合

开发、测试、正式环境必须使用同一迁移集合。

禁止：

- 为正式环境维护一套不同 SQL；
- 手工在正式库执行未纳入迁移集合的结构变更；
- 在开发库通过手改结构绕过迁移；
- 在测试库长期保留无法由迁移重建的特殊结构。

允许：

- 环境变量控制连接目标；
- 不同环境使用不同账号、数据库名、实例规格；
- 测试环境额外执行测试 fixture；
- 隔离验证环境执行非正式迁移原型。

### 7.2 环境专用配置

环境差异不得写进业务迁移 SQL。

可通过部署配置管理：

- 数据库连接串；
- 角色密码；
- statement timeout；
- 连接池参数；
- 备份策略；
- 扩展安装权限。

业务 schema、约束、触发器和视图必须一致。

## 8. 文件数量范围

按 47 张 M1 业务表、1 张 `system_state` 控制表、主要函数/触发器/视图估算，正式迁移文件数量建议控制在：

- 表与基础约束：25-40 个；
- 后置 FK、唯一索引、部分索引：8-15 个；
- 触发器函数和绑定：8-15 个；
- 受控切换函数：4-8 个；
- 读取视图：4-8 个；
- 权限和默认权限：3-6 个。

总量建议：约 50-90 个迁移文件。

如果明显少于 30 个，通常意味着文件过大、不利于审查。如果超过 120 个，通常意味着对象被拆得过碎、迁移审查成本过高。

## 9. 伪 SQL 展示边界

文档中允许出现短小伪 SQL，用于表达不变量或事务边界。

禁止在文档阶段形成：

- 完整可执行建表脚本；
- 可直接复制到 `migrations/` 的函数体；
- 正式数据回填脚本；
- 真实业务数据 fixture；
- 自动应用运营确认结果的 SQL。

示例格式：

```sql
-- 伪 SQL，不是正式迁移脚本。
begin;
  acquire controlled lock;
  validate expected state;
  switch version statuses;
  deferred triggers verify invariants;
commit;
```

## 10. 审查清单

每个迁移文件进入非正式原型前必须回答：

- 属于哪个 Layer；
- 是否依赖前置文件；
- 是否能在事务中执行；
- 是否修改权威事实；
- 是否引入业务规则或阈值；
- 是否需要独立验证脚本；
- 是否需要生产备份点；
- 是否会影响应用账号权限；
- 是否会改变 active 版本可见性；
- 是否有 forward fix 策略。

## 11. 结论

采用 4 位层级目录 + 3 位层内序号的命名方式，正式迁移文件采用 Flyway 风格 `V{layer4}_{seq3}__description.sql`，视图和可替换函数可评估 `R{layer4}_{seq3}__description.sql`。

本规范允许下一步生成非正式迁移原型目录设计和样例文件清单，但不允许生成正式迁移 SQL。

v0.3 同步要求：所有涉及作品 ID 的迁移、触发器和验证脚本必须引用单一权威解析函数；`12345` 与 `Y12345` 作为不同完整原始 ID 处理，二者可映射到同一标准作品 ID；授权分类不得参与业务形态推断。
