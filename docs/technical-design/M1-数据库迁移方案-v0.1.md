# M1 数据库迁移方案 v0.1

## 0. 当前权威状态（2026-06-21 Flyway 候选轮次）

- 迁移实现唯一基线：`M1-物理数据模型-v0.4.md`。
- `M1-物理数据模型-v0.3.md` 已归档为历史设计，不再作为实现依据。
- Flyway SQL-only 与 forward-only 原则保持冻结。
- 正式候选文件只能先放在 `experiments/m1-flyway-candidate/migrations/`；本轮仍不得写入正式 `db/migrations/`。
- Flyway history 位置冻结为 `flyway_history.flyway_schema_history`，业务对象 schema 为 `m1`，避免 history 表干扰 M1 48 张表口径。
- 正式候选验证要求数据库迁移会话使用 UTC；上一轮非正式原型实例曾使用 `Asia/Shanghai`，本轮候选已通过 UTC 会话验证。

## 1. 迁移设计基线

M1 当前采用 PostgreSQL 16+，权威金额类型为 `NUMERIC(32,18)`，M1 物理模型口径为 47 张 M1 业务表 + 1 张 `system_state` 控制表，共 48 张物理表。迁移设计必须支持：

- 不可变收入事实；
- 批次、映射版本和派生投影的原子可见性切换；
- 完整精确十进制金额；
- 文件指纹、导入批次、问题决定、映射变更和恢复点的可追溯；
- 初始化、首次激活、后续批次激活、撤销、受控重导和基础信息版本切换；
- 正式库、测试库和开发库隔离；
- 未经确认的业务字段、阈值、分类值和标签值不得写死到迁移中。

本方案只给出迁移结构和可实现性设计。所有 SQL 片段均为伪代码示例，不得作为正式迁移脚本直接保存或执行。

## 2. 三个物理模型细节收口

### 2.1 历史原始作品 ID 唯一性

#### 2.1.1 已冻结规则

同一个 `mapping_version` 中：

1. `historical_volume_mapping.historical_raw_work_id` 不得因为 `business_form` 不同而重复；
2. `business_form` 必须与已确认的完整原始 ID 前缀规则一致：`^[0-9]+$` 为有声版权，`^Y[0-9]+$` 为有声成品；
3. 同一个原始作品 ID 不得同时存在于 `raw_work_id_mapping.raw_work_id` 与 `historical_volume_mapping.historical_raw_work_id`；
4. 历史分册 ID 不创建独立 `standard_work` 记录，只映射到 `target_standard_work_id`；
5. `12345` 与 `Y12345` 是两个不同的完整原始作品 ID，但可映射到同一标准作品 ID `12345`；
6. 授权分类不得反向覆盖业务形态；
7. 不根据出现频率、金额、名称相似度自动决定历史分册归并。

#### 2.1.2 方案比较

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| 延迟约束触发器 | 在两张映射表上使用 `DEFERRABLE INITIALLY DEFERRED` constraint trigger，提交前检查跨表冲突，并锁定对应 `mapping_version` 行序列化同版本构建 | 不增加业务表；保持 47 张 M1 业务表 + 1 张控制表的 v0.3 口径；适合完整快照版本构建 | 需要编写和测试触发器函数；并发构建同版本时必须依赖版本行锁或 advisory lock | 推荐 |
| 统一登记表 | 新增 `mapping_raw_work_id_registry(mapping_version_id, raw_work_id, mapping_kind)`，两张映射表引用登记表，由唯一约束天然阻断冲突 | 约束表达清晰；跨表唯一性由普通唯一键承担 | 新增物理表，M1 业务表数从 47 增加；写入路径多一步；迁移和模型需调整更多 | 暂不采用 |
| 视图或表达式索引 | 尝试在 union 视图或表达式上实现跨表唯一 | 不改变原表 | PostgreSQL 不能直接在普通视图上建立跨基表唯一约束；无法可靠承担写入期不变量 | 放弃 |

唯一推荐：使用“延迟约束触发器 + 同版本行锁”的实现方案。

需要同步修订物理模型 v0.3：

- `historical_volume_mapping` 的版本内唯一约束调整为 `UNIQUE(mapping_version_id, historical_raw_work_id)`；
- 取消任何可能允许同一历史原始 ID 因 `business_form` 不同而重复的唯一约束表述；
- Layer 6 增加跨表约束触发器，覆盖 `raw_work_id_mapping` 与 `historical_volume_mapping`；
- 触发器检查必须在同一 `mapping_version_id` 范围内执行，并锁定父 `mapping_version` 行，防止并发事务互相绕过。

伪 SQL 示例：

```sql
-- 伪 SQL，仅表达不变量，不是正式迁移脚本。
-- 1. historical_volume_mapping 内部唯一：
unique (mapping_version_id, historical_raw_work_id)

-- 2. 提交前跨表检查：
on insert/update/delete of raw_work_id_mapping or historical_volume_mapping
deferrable initially deferred
begin
  lock selected mapping_version row for update;
  assert no raw_work_id appears in both mapping tables under same mapping_version;
  assert historical_raw_work_id business_form matches confirmed prefix rule;
end;
```

业务形态与前缀规则的具体值不得在迁移中散落硬编码。若前缀规则已冻结，可由受控检查函数读取冻结配置；若仍需配置化，应在迁移原型阶段把规则来源显式纳入校验函数设计。

### 2.2 新标准作品与基础信息版本关系

#### 2.2.1 推荐结论

标准作品身份可以由账单批次独立新增，不要求每次账单批次激活时同步复制全量基础信息版本。

`basic_info_version` 继续采用全量快照语义，但需要修订为：

> 全量快照指“已进入正式基础信息版本作用域的作品，在同一个 active 基础信息版本中都有完整的当前快照行”；它不等同于“`standard_work` 身份全集在任意时刻都必须已有基础信息行”。

因此：

- `standard_work` 是标准作品身份全集的权威来源；
- `basic_info_version_work` 是正式应用过的基础信息快照；
- 新作品尚未进入正式基础信息版本时，仍保留在 `standard_work`，并由缺口视图识别为基础信息缺失；
- M2 完整性视图必须从 `standard_work` 左连接当前基础信息版本，而不是以内连接方式丢失新作品；
- 账单批次激活不强制生成新的基础信息版本；
- 基础信息补全应用批次才生成新的 `basic_info_version`。

#### 2.2.2 对“全量快照”的修订边界

需要同步修订物理模型 v0.3：

1. `basic_info_version` 章节增加“快照作用域”定义；
2. `basic_info_version_work` 的唯一约束仍为 `UNIQUE(basic_info_version_id, standard_work_id)`；
3. active 基础信息版本的提交校验不再要求覆盖全部 `standard_work`；
4. 校验要求改为：
   - 同一版本内同一标准作品最多一行；
   - 版本引用的 `classification_release_id` 与 `tag_release_id` 一致；
   - 已纳入该版本的作品基础信息字段满足该版本的字段校验；
   - 未纳入该版本的 `standard_work` 由缺口视图报告，而不是阻断账单事实入库；
5. `v_basic_info_gap` 和 `v_basic_info_m2_completeness` 必须以 `standard_work` 为左表。

伪视图示例：

```sql
-- 伪 SQL，仅表达读取语义。
select
  sw.standard_work_id,
  biw.standard_work_name,
  biw.author_id,
  case when biw.standard_work_id is null then true else false end as missing_basic_info
from standard_work sw
left join active_basic_info_version abiv on true
left join basic_info_version_work biw
  on biw.basic_info_version_id = abiv.id
 and biw.standard_work_id = sw.standard_work_id;
```

这不改变已确认业务规则：进入 M2 正式评估的作品仍必须具备标准作品名称、作者、一级至三级分类、版权开始日期、版权到期日期、必需标签和已确认归并关系。

### 2.3 初始化阶段 active 版本语义

#### 2.3.1 系统生命周期状态

已冻结新增独立控制对象 `system_state`，作为 M1 数据库生命周期的权威状态。该对象属于 Layer 0 控制表，不承载业务事实；物理模型 v0.3 已明确“47 张 M1 业务表 + 1 张控制表 = 48 张物理表”的统计口径。

生命周期状态：

| 状态 | 含义 | active 版本要求 |
|---|---|---|
| `schema_initialized` | schema、角色、迁移元数据和基础约束已建立 | 允许 0 个 active 映射版本、基础信息版本、分类 release、标签 release |
| `master_data_initializing` | 正在装载基础身份、空 release、清洗规则和结构性配置 | 允许 0 个 active；不允许业务批次激活 |
| `ready_for_bill_activation` | 首个账单激活前的准备状态；四类 bootstrap 版本已经原子激活 | 映射、基础信息、分类 release、标签 release 各恰好 1 个 active；不允许 0 个 |
| `operational` | 系统正式运行，可进行批次激活、撤销、映射切换和基础信息应用 | 上述四类版本必须各恰好 1 个 active |

首版激活建议：

1. 初始化期间不禁用约束；
2. 通过受控函数创建 bootstrap active 版本：
   - 空或最小可运行 `mapping_version`；
   - 空作用域 `basic_info_version`；
   - 空或结构性 `classification_release`；
   - 空或结构性 `tag_release`；
3. 受控初始化函数在同一事务内创建或校验四类 bootstrap 版本、将四类对象各激活一个，并把 `system_state.lifecycle_status` 从 `master_data_initializing` 切换到 `ready_for_bill_activation`；
4. 首个账单批次激活时，在同一短事务中退休 bootstrap mapping、激活包含首批事实投影的真实 mapping、激活批次并切换到 `operational`；基础信息、分类和标签 bootstrap 版本可继续 active；
5. `ready_for_bill_activation` 和 `operational` 在提交时均拒绝任一类 0 个或 2 个 active 版本。

#### 2.3.2 约束识别初始化状态

延迟约束触发器和受控函数读取 `system_state`，而不是禁用约束或人工临时修改数据库。

伪逻辑：

```sql
-- 伪 SQL，仅表达状态门禁。
if system_state.lifecycle_status in ('schema_initialized', 'master_data_initializing') then
  allow zero active versions;
  reject ordinary switch functions;
else
  require exactly one active mapping_version;
  require exactly one active basic_info_version;
  require exactly one active classification_release;
  require exactly one active tag_release;
end if;
```

物理模型 v0.3 已同步：

- 新增 `system_state` 控制对象；
- `mapping_version`、`basic_info_version`、`classification_release`、`tag_release` 的“最多一个 active”仍由部分唯一索引保证；
- “至少一个 active”改由读取 `system_state` 的 deferred constraint trigger 保证；
- 批次激活仅可在 `ready_for_bill_activation` 或 `operational` 执行；撤销、纯映射切换和基础信息切换仅可在 `operational` 执行；
- 初始化状态迁移只能通过受控函数完成。

## 3. 迁移分层

### 3.1 分层总览

| 层级 | 名称 | 主要对象 | 依赖 | 是否可独立部署 | 失败处理 |
|---|---|---|---|---|---|
| Layer 0 | 数据库基础 | PostgreSQL 版本门禁、扩展、schema、角色、默认权限、迁移元数据、`system_state` | 无 | 可单独部署 | 失败后清理空 schema 或重建隔离库；正式环境需恢复到迁移前备份点 |
| Layer 1 | 基础身份与平台表 | 后台任务、任务事件、文件指纹、清洗规则、渠道、标准作品、作者、分类/标签 release 身份 | Layer 0 | 可单独部署 | 未写入业务事实，结构失败可前向修复或重建环境 |
| Layer 2 | 导入、暂存、问题与批次 | import file、staging、issue run、问题、决定、批次、覆盖月份、收入事实 | Layer 1；部分 FK 依赖 Layer 3 的版本身份时可后置添加 FK | 可部署，但不允许业务激活 | 失败不得保留半建约束；通过修复迁移补齐 |
| Layer 3 | 映射、投影与版本指标 | mapping version、channel alias、raw work mapping、historical volume mapping、income projection、首次实销指标、映射变更 | Layer 1、2 | 可部署；激活函数在 Layer 6 | 结构失败不影响已建事实表；修复后再开放激活 |
| Layer 4 | 基础信息版本 | basic info version、作者别名、分类节点、标签、作品分类/标签分配、导出/上传/临时记录/问题/应用批次 | Layer 1、3；分类/标签 release 身份已存在 | 可部署；不要求 3,099 部基础信息已补齐 | 保留缺口视图；失败不能阻断账单事实结构 |
| Layer 5 | 恢复、影响与审计 | 月份完整性、恢复点、撤销、影响事件、消费者状态、变更审计 | Layer 2、3、4 | 可部署；被 Layer 6 函数使用 | 失败时不开放撤销/恢复函数 |
| Layer 6 | 可编程数据库对象 | 不可变触发器、deferred constraint triggers、批次激活/撤销/版本切换函数、正式读取视图、权限授予 | Layer 0-5 | 应作为一个门禁层部署 | 失败时不得开放应用账号；修复后重新验证 |

### 3.2 Layer 0：数据库基础

Layer 0 负责建立迁移运行的最低公共基础：

- PostgreSQL 版本：16+；
- schema：建议至少区分 `m1_core`、`m1_private`、`m1_audit`、`m1_control`；
- 角色：`migration_owner`、`application_rw`、`application_ro`、`background_worker`、`backup_operator`；
- 默认权限：撤销 `public` 默认权限，显式授权；
- 时区与连接设置：
  - 权威时间字段使用 `timestamptz`；
  - 数据库连接默认 `TimeZone='UTC'`；
  - 自然月字段使用 `date` 且必须为月初；
  - 中文显示和运营日期格式由应用或导出层处理；
- 必需扩展：
  - 初版不强制依赖扩展；
  - 如需数据库内计算 digest 或随机 token，可在隔离验证后引入 `pgcrypto`；
  - `pg_stat_statements` 可作为运维监控扩展，不写入业务迁移硬依赖；
- migration metadata 表：由迁移工具维护；
- `system_state`：M1 生命周期控制对象。

### 3.3 Layer 1：基础身份与平台表

包含：

- `background_task`；
- `background_task_event`；
- `file_fingerprint_registry`；
- `cleaning_rule_version`；
- `channel`；
- `standard_work`；
- `author`；
- `classification_system`；
- `classification_release`；
- `tag_release`。

设计要点：

- 平台表不依赖正式收入事实；
- `file_fingerprint_registry` 是 SHA-256 和文件大小的唯一权威；
- `standard_work` 只保存身份，不保存当前基础信息指针；
- `classification_release` 和 `tag_release` 的 active 语义受 `system_state` 门禁影响。

### 3.4 Layer 2：导入、暂存、问题与批次

包含：

- `import_file`；
- `bill_staging_session`；
- `temp_bill_record`；
- `issue_run`；
- `data_issue`；
- `data_issue_decision`；
- `import_batch`；
- `import_batch_file`；
- `import_batch_month`；
- `income_fact`。

设计要点：

- 临时表允许空值并生成问题；
- 正式 `income_fact` 七个业务字段、来源工作表、金额和月份均为 `NOT NULL`；
- `income_fact` 原始字段和金额不可修改；
- 批次达到 `ready` 前必须完成严格对账，但对账跨表条件由 Layer 6 的函数和约束触发器最终保证；
- 受控重导只允许从已撤销批次发起，不继承旧问题处理决定。

### 3.5 Layer 3：映射、投影与版本指标

包含：

- `mapping_version`；
- `channel_alias`；
- `raw_work_id_mapping`；
- `historical_volume_mapping`；
- `income_projection`；
- `mapping_version_work_metric`；
- `mapping_version_work_form_metric`；
- `mapping_change_record`；
- `work_business_form`；
- `standard_work_status_history`。

设计要点：

- 映射版本采用完整快照；
- 当前有效性只由 `mapping_version.status='active'` 决定；
- `income_projection` 不复制金额和月份，只通过 `income_fact_id` 读取；
- `historical_volume_mapping` 使用 `historical_raw_work_id`，不创建历史标准作品；
- 跨表原始作品 ID 唯一性由 Layer 6 的延迟约束触发器保证；
- 首次正数实销指标在候选版本中预构建，切换事务内不做大范围重算。

### 3.6 Layer 4：基础信息版本

包含：

- `basic_info_version`；
- `basic_info_version_work`；
- `author_alias`；
- `classification_node`；
- `tag`；
- `work_classification_assignment`；
- `work_tag_assignment`；
- `basic_info_export`；
- `basic_info_upload`；
- `basic_info_temp_record`；
- `basic_info_issue`；
- `basic_info_apply_batch`。

设计要点：

- 基础信息版本是“已进入基础信息版本作用域”的全量快照；
- 新 `standard_work` 不要求立即进入基础信息版本；
- 缺口视图必须保留新作品，不得以内连接丢失；
- `签订日期` 对应版权开始日期，`到期时间` 对应版权到期日期；
- 两种业务形态共享标准作品层版权期限；
- 分类结构支持固定三级路径，但具体分类值仍可后续导入；
- 标签区分辅助内容标签和特殊属性标签，具体值仍可保持 PENDING-DATA。

### 3.7 Layer 5：恢复、影响与审计

包含：

- `month_completeness_confirmation`；
- `restore_point`；
- `import_batch_undo`；
- `batch_impact_record`；
- `batch_impact_consumption`；
- `mapping_change_record`。

设计要点：

- 不完整月份收入事实继续保存，但不得作为正式评估截止月份；
- 区分账单最大月份和最新已确认完整月份；
- 撤销是业务状态与映射版本切换，不是物理删除；
- M2、M4 等消费者各自记录影响消费状态；
- 恢复点记录业务版本、checksum 和备份位置，不替代数据库备份/PITR。

### 3.8 Layer 6：可编程数据库对象

包含：

- 不可变触发器；
- deferred constraint triggers；
- 批次激活函数；
- 批次撤销函数；
- 纯映射版本切换函数；
- 基础信息版本切换函数；
- 当前读取视图；
- 权限授予。

关键边界：

- 大文件解析、投影重建、指标重算在长任务中完成；
- 可见性切换必须是短事务；
- 事务中使用固定 advisory lock key 序列化批次/映射切换；
- 应用账号不得直接更新版本状态；
- `SECURITY DEFINER` 函数必须固定 `search_path`，并校验调用角色。

## 4. 迁移工具建议

### 4.1 候选比较

| 方案 | 事务迁移 | checksum | forward-only | 函数/触发器/复杂约束 | dry run | 状态追踪 | CI 集成 | 与未来应用框架耦合 |
|---|---|---|---|---|---|---|---|---|
| Flyway SQL-only | PostgreSQL 下默认单迁移事务；可按文件控制 | 支持 | 适合 forward-only；修复通过新版本迁移 | 原生 SQL，适合函数、触发器、视图 | 可用隔离实例模拟；部分 dry-run 能力取决于版本/授权 | 内置 schema history | 成熟 | 低 |
| Node 生态迁移工具 | 取决于工具和写法 | 通常支持或可自建 | 可实现 | 复杂 PL/pgSQL 容易被 JS DSL 干扰；建议写 raw SQL | 取决于工具 | 支持 | 好 | 中到高，受未来框架选择影响 |
| Sqitch / PostgreSQL 专用风格 | 依赖和 verify 能力强 | 支持变更追踪 | 可约束生产 forward-only | 非常适合数据库对象 | verify 强，dry-run 需流程设计 | 内置 | 好 | 低 |

唯一推荐并冻结：Flyway SQL-only。

推荐理由：

- 当前尚无应用技术栈，Flyway 不绑定 Node、Python 或具体框架；
- checksum、schema history 和 CI 集成成熟；
- SQL-only 模式适合 PostgreSQL 函数、触发器、部分索引、`NULLS NOT DISTINCT` 和 constraint trigger；
- 可以采用 forward-only 生产原则；
- 隔离 PostgreSQL 16 实例可以承担 dry-run 和真实创建验证，不依赖正式环境。

本轮不安装工具、不生成配置、不创建迁移文件。后续正式迁移集合必须使用同一 Flyway SQL-only 规范。

## 5. 正向迁移与回滚策略

### 5.1 正式原则

正式迁移采用 forward-only 原则。

不要求每条迁移都有可自动执行的 down migration。数据库不是视频播放器，破坏性变更不能假设能安全倒放。

### 5.2 变更分类

| 类别 | 示例 | 策略 |
|---|---|---|
| 完全可逆 | 新增空表、无引用索引、只读视图、未被使用的函数 | 开发/测试可自动回滚；生产优先前向修复 |
| 结构可逆但数据不可逆 | 新增列并回填、状态字段重算、checksum 重建 | 生产不自动 down；必须先备份，再用修复迁移或业务恢复点 |
| 不可逆，只能前向修复 | 删除列、类型收窄、拆表后删除旧字段、历史版本清理 | 不生成自动 down；用新迁移修复或重新发布兼容结构 |
| 需要数据库备份/PITR | 误删事实、错误覆盖权威金额、错误批量更新历史版本 | 使用备份、WAL/PITR 和恢复演练；业务版本回滚不能替代数据库恢复 |

### 5.3 生产失败处理

- 迁移在提交前失败：依赖事务自动回滚，状态表不记录成功；
- 迁移提交后发现结构缺陷：生成新的 forward fix migration；
- 数据破坏风险：停止写入，使用备份/PITR 或恢复点评估；
- 业务版本回滚：通过映射版本、基础信息版本或批次撤销完成；
- schema 回滚：仅在隔离环境使用；生产必须经单独审批。

### 5.4 破坏性变更规则

- 删除列前至少经历一个兼容发布周期；
- 类型收窄必须有全量扫描证明不会截断；
- 历史版本清理必须先冻结保留策略，并生成可审计清单；
- 权威事实表原则上不做破坏性清理；
- 清理真实账单原始文件不属于数据库迁移，由数据留存策略单独管理。

## 6. 权限设计

### 6.1 角色

| 角色 | 用途 | 权限边界 |
|---|---|---|
| `migration_owner` | 执行迁移、创建 schema、表、索引、函数、触发器、授权 | 不作为应用运行账号；只在迁移窗口使用 |
| `application_rw` | 常规应用读写 | 不得直接修改 `income_fact`、版本状态、映射快照和恢复点；通过受控函数间接操作 |
| `application_ro` | 只读查询和分析 | 只访问正式读取视图和必要字典表；不能访问 staging 私有明细 |
| `background_worker` | 后台任务、投影构建、校验和批次操作 | 可写 staging、候选版本和任务表；版本激活只能调用受控函数 |
| `backup_operator` | 备份、恢复、PITR 演练 | 不参与业务写入；权限限于备份恢复所需能力 |

### 6.2 `SECURITY DEFINER` 边界

受控函数可以使用 `SECURITY DEFINER`，但必须满足：

- 函数 owner 使用专门角色，不使用超级用户；
- 函数内部固定 `SET search_path = m1_core, m1_audit, pg_temp`，不得依赖调用方 search_path；
- 函数开头校验调用角色；
- 所有动态 SQL 必须避免拼接未验证标识符；
- 切换函数内部获取 advisory lock 和必要行锁；
- 函数只暴露业务意图参数，不暴露任意状态更新入口。

### 6.3 应用账号禁区

应用账号不得：

- 直接 `UPDATE income_fact`；
- 直接把 `mapping_version`、`basic_info_version`、`classification_release`、`tag_release` 改为 `active`；
- 直接绕过 `issue_run` 写问题决定；
- 直接删除批次、事实、版本、恢复点和审计记录；
- 直接访问被定义为私有或敏感的原始明细导出。

只读分析账号通过正式视图访问：

- `v_current_income_projection`；
- `v_income_projection_monthly`；
- `v_current_work_metrics`；
- `v_current_basic_info`；
- `v_basic_info_gap`；
- `v_bill_cutoff`。

## 7. 迁移门禁

### 7.1 允许生成非正式迁移原型的条件

- 本轮四份设计文档通过审查；
- 历史原始作品 ID 唯一性、新标准作品与基础信息版本关系、初始化 active 语义完成收口；
- Git 忽略规则确认仍覆盖真实账单、台账、私有确认包和临时分析目录；
- PostgreSQL 16 隔离测试环境方案明确；
- 明确非正式原型不得连接正式库、不得导入正式数据、不得放入正式 `migrations/` 目录。

### 7.2 允许生成正式迁移文件的条件

- 非正式原型在隔离 PostgreSQL 16 实例通过；
- DDL、触发器、函数、部分索引、`NULLS NOT DISTINCT`、deferred constraint trigger 全部真实创建并测试；
- 不存在未经确认的业务字段、分类值、标签值、阈值或自动判断规则被写死；
- 迁移工具 Flyway SQL-only、目录、命名、checksum 和 forward-only 规范冻结；
- 权限模型通过最小权限测试；
- 生产备份、恢复和迁移窗口策略明确。

### 7.3 允许正式数据迁移的条件

- 346 个正式导入阻断组解决；
- 金额、年月、作品 ID 等关键空值和异常 ID 修正；
- 85 个多 ID 归并按迁移范围确认；
- 严格对账通过；
- 备份和恢复演练通过；
- 运营确认结果以受控导入流程进入候选版本，不得手工改正式表；
- 正式库与开发/测试库隔离验证通过。

## 8. 结论

推荐迁移工具为 Flyway SQL-only。迁移设计采用 7 层结构：Layer 0 至 Layer 6。

本方案允许下一步生成“非正式迁移原型”设计和临时验证脚本，但仍不允许生成正式迁移文件、不允许连接正式数据库、不允许导入正式或测试业务数据。

`M1-物理数据模型-v0.3.md` 已同步以下内容：

1. `historical_volume_mapping` 版本内唯一性与跨表唯一性触发器；
2. `basic_info_version` 基础信息作用域全量快照语义；
3. `system_state` 控制对象；
4. active 版本“最多一个”和“至少一个”的初始化状态门禁；
5. `v_basic_info_gap` / `v_basic_info_m2_completeness` 以 `standard_work` 为左表的读取语义；
6. 作品 ID 与业务形态单一权威解析规则；
7. Flyway SQL-only 与 forward-only 冻结结论。

## 9. PostgreSQL 16 原型验证后的补充冻结

2026-06-21 的 PostgreSQL 16.14 隔离验证进一步冻结：

- `ready_for_bill_activation` 与 `operational` 均要求四类版本各恰好一个 active；
- mapping/basic_info/classification/tag 的版本头激活约束必须同时覆盖各自快照子表，不允许对 validated/active/retired 快照追加或改写；
- `income_fact` 只允许在批次为 draft/validating 时新增，ready 后事实集合与严格对账字段冻结；
- 基础信息版本引用新分类或标签 release 时，三者在同一受控事务切换；
- SECURITY DEFINER 函数必须固定 `search_path=pg_catalog,m1`，内部切换上下文同时校验执行身份，不得只信任调用方可设置的自定义 GUC；
- Flyway SQL-only 和 forward-only 结论不变，原型 SQL 不构成 Flyway history。

以上内容由《M1-物理数据模型-v0.4.md》收口。非正式原型 76 项验证全部通过后，技术上允许进入“正式 Flyway 迁移文件整理与审查”阶段；正式数据迁移门禁保持不变。
