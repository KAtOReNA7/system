# M2-B-3.2b local dry-run input manifest validator implementation report v0.1

## 1. Scope

This round implements the technical-line M2-B-3.2b local dry-run input manifest validator.

The validator is a no-db metadata validator. It only reads a manifest file body. It does not follow any `fileName`, `sourcePath`, `path`, or `uri` value declared inside the manifest.

This round does not implement local dry-run execution.

## 2. Authorization boundary

The implementation follows the operations authorization recorded in:

- `docs/analysis/m1-master-data/M2-local-dry-run-manifest-and-environment-authorization-report-v0.1.md`
- `docs/analysis/m1-master-data/M2-local-dry-run-manifest-and-environment-authorization-summary-v0.1.json`

Authorized:

- sanitized or synthetic manifest metadata may enter Git;
- manifest validator may be implemented;
- stage summary metadata may be represented only through sanitized manifest metadata;
- operations confirmation metadata may be represented only through sanitized manifest metadata.

Not authorized:

- manifest source file body read;
- stage JSON body read;
- operations confirmation body read;
- `data/` directory read;
- local environment file read;
- database connection string read;
- database connection;
- Docker execution;
- local write;
- migration;
- local dry-run mode;
- write API, export API, or evaluation task API.

## 4. Validator read scope

The validator reads only:

- default sanitized manifest fixture; or
- the explicit `--manifest <path>` manifest file.

The validator does not recursively scan the repository and does not follow manifest-declared source references.

## 5. Validator prohibited scope

The validator does not:

- read `data/`;
- read stage JSON body;
- read operations confirmation result body;
- read source file body referenced by manifest metadata;
- read `.env`, `.env.local`, or `.pgpass`;
- read database connection strings;
- connect to any database;
- execute Docker;
- perform network calls;
- modify the manifest file;
- generate local dry-run results;
- generate or activate `mapping_version`;
- call `switch_mapping_version`;
- modify `db/migrations/`;
- add API, page, write API, export API, evaluation task API, formal mode, or local dry-run mode.

## 6. Sanitized manifest fixture

The fixture is `test/fixtures/m2LocalDryRunSanitizedManifest.fixture.json`.

It contains only synthetic or sanitized metadata:

- manifest kind;
- dataset boundary;
- no-db authorization flags;
- source IDs;
- source type;
- safe basename file names;
- synthetic hashes;
- record counts;
- month ranges;
- field names, types, and purposes;
- range summary flags confirming no real amounts, work names, author names, channel names, stage JSON body, or operations confirmation body.

It does not contain real works, authors, channels, amounts, business IDs, private paths, source file body, stage JSON body, operations confirmation body, or database connection details.

## 7. Validation rules

The validator checks:

- valid JSON;
- `manifestVersion` present;
- `manifestKind = m2-local-dry-run-input-manifest`;
- `datasetBoundary = sanitized-metadata-only`;
- all no-db authorization flags remain false where required;
- `sources` is a non-empty array;
- required source metadata is present;
- `sourceType` is one of `synthetic`, `fixture`, `stage-summary`, or `ops-summary`;
- `fileName` is a basename only;
- hash is 64 lowercase hexadecimal characters;
- `recordCount` is a non-negative integer;
- `monthRange.from` and `monthRange.to` use `YYYY-MM`;
- `fieldList` contains only field metadata, not value samples;
- `rangeSummary` explicitly marks real data and source bodies as false;
- prohibited keys such as body, rows, records, raw data, source body, stage JSON body, operations confirmation body, database URL, connection string, password, secret, or token are absent;
- suspicious URL, connection, private path, environment, or data-directory patterns are absent.

## 8. Output JSON

Success and failure both write JSON to stdout.

Success uses exit code `0`; failure uses a non-zero exit code.

The output includes:

- status;
- mode;
- stage;
- manifestPathType;
- sourceCount;
- metadataOnly;
- source/body/database/Docker guard booleans;
- capability guard booleans;
- M2-C and M2-D readiness booleans;
- findings.

Failure findings include only sanitized codes and messages. They do not echo manifest source content, private paths, database URLs, SQL, stack traces, host details, or real business data.
