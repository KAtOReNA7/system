# M1 迁移验收清单 v0.1

## 0. 当前门禁结论（2026-06-21 Flyway 候选验证后）

- 已允许生成并审查正式命名格式的 Flyway SQL-only 迁移候选。
- 候选仍未晋升到正式 `db/migrations/`，也不构成正式 migration history。
- 候选已在 `m1_flyway_candidate_a` 与 `m1_flyway_candidate_b` 两个全新本地隔离 PostgreSQL 16 库中通过迁移和回归。
- 若独立审查无未解决 HIGH 风险，允许将完全相同候选文件作为下一步晋升对象；晋升前不得改写已验证文件内容。
- 正式数据迁移门禁仍保持不变：不得导入真实账单、数字版权台账、运营确认结果或真实作品信息。

## 2. 三项物理模型细节验收

### 2.1 历史原始作品 ID 唯一性

| 检查项 | 通过标准 |
|---|---|
| 同版本历史 ID 不因业务形态重复 | `historical_volume_mapping` 版本内唯一性按 `(mapping_version_id, historical_raw_work_id)` 表达 |
| 跨表冲突阻断 | 同一原始 ID 不得同时出现在常规映射和历史分册映射 |
| 业务形态前缀一致 | business_form 与已确认原始 ID 前缀规则一致 |
| PostgreSQL 可实现 | 使用 deferred constraint trigger + 同版本行锁或等价可验证方案 |
| 不新增自动归并规则 | 不按名称相似、出现次数或金额自动选择目标作品 |

### 2.2 新标准作品与基础信息版本

| 检查项 | 通过标准 |
|---|---|
| 标准作品身份独立 | 账单批次可新增 `standard_work` 身份 |
| 不强制同步基础信息版本 | 批次激活不要求复制基础信息快照 |
| 缺口视图保留新作品 | 基础信息缺失通过左连接视图识别 |
| 全量快照语义修订 | 全量快照限定为已进入基础信息版本作用域的完整快照 |
| M2 门禁不放松 | M2 正式评估仍要求对应作品基础信息完整 |

### 2.3 初始化 active 语义

| 检查项 | 通过标准 |
|---|---|
| 生命周期状态明确 | 至少包含 `schema_initialized`、`master_data_initializing`、`ready_for_bill_activation`、`operational` |
| 初始化允许 0 active | 初始化阶段不需要临时禁用约束 |
| ready/运行阶段恰好 1 active | `ready_for_bill_activation` 与 `operational` 阶段映射、基础信息、分类 release、标签 release 各 1 个 active |
| 首版激活受控 | bootstrap 四类 active 版本由受控函数在同一事务创建或校验并激活，再切换到 ready |
| 约束识别状态 | deferred trigger 或函数读取 `system_state` 判断门禁 |

### 2.4 作品 ID 与业务形态规则

| 检查项 | 通过标准 |
|---|---|
| 完整原始 ID 独立 | `12345` 与 `Y12345` 不被视为同一原始作品 ID |
| 标准作品 ID 派生 | 二者均可映射到标准作品 ID `12345` |
| 业务形态派生 | 纯数字为有声版权，Y 前缀为有声成品 |
| 授权分类边界 | 授权分类变化不得改变业务形态 |
| 非法 ID 阻断 | 非法格式进入数据问题，不猜测修正 |
| 单一权威函数 | 触发器、视图和分析脚本不得散落不同正则 |

## 6. 迁移文件审查清单

每个正式迁移文件必须检查：

- 文件名符合 `V{layer4}_{seq3}__description.sql` 或已冻结的等价格式；
- 所属 Layer 明确；
- 依赖前置对象明确；
- 可事务执行性明确；
- 是否包含不可逆变更明确；
- 是否需要备份点明确；
- 是否涉及权威事实表明确；
- 是否引入业务规则明确；
- 是否含真实业务数据：必须为否；
- 是否含环境专用密码或连接串：必须为否；
- 是否改变权限：如改变，必须有授权清单；
- 是否需要配套隔离测试；
- 是否有 forward fix 策略。

## 7. 高风险场景验收

最高风险场景必须在隔离 PostgreSQL 16 中覆盖：

1. 两个批次激活事务并发；
2. 批次激活提交前投影缺失；
3. 批次已 active 但投影未包含该批次的违规状态；
4. 批次已 revoked 但 active 投影仍包含该批次的违规状态；
5. 同一原始作品 ID 同版本跨两张映射表冲突；
6. `historical_raw_work_id` 因 `business_form` 不同重复；
7. 初始化阶段 0 active 与运行阶段 0 active 的差异；
8. 新标准作品没有基础信息记录但必须出现在缺口视图；
9. `NUMERIC(32,18)` 18 位小数聚合；
10. `SECURITY DEFINER` search_path 被恶意调用方影响的防护。

## 8. 不得通过项

以下任一情况出现，迁移不得进入下一阶段：

- 正式迁移文件在未批准前生成；
- 连接正式数据库；
- 导入真实账单明细或台账明细；
- 应用账号可直接修改 `income_fact`；
- 应用账号可直接切换 active 版本；
- 需要禁用约束才能初始化；
- active 版本约束在初始化和运行状态下无法区分；
- 跨表原始作品 ID 冲突无法由数据库阻断；
- 新作品因没有基础信息记录而从缺口视图消失；
- PENDING-DATA 值被写死；
- 修改已执行迁移文件而非追加修复迁移。

## 9. 输出结论模板

每次迁移方案或原型验证完成后，必须输出：

1. 推荐迁移工具；
2. 迁移层数；
3. 实际文件和目录数量；
4. forward-only 与回滚原则是否仍成立；
5. 已覆盖的最高风险场景；
6. 未通过项；
7. 仍需业务或运营确认事项；
8. 是否允许进入下一门禁。

## 10. 当前结论

历史结论：当前只允许进入“非正式迁移原型”准备阶段。该历史结论已被 2026-06-21 Flyway 候选验证结论取代。

仍不得：

- 生成正式迁移文件；
- 连接正式数据库；
- 导入正式或测试业务数据；
- 编写应用代码、接口或页面；
- 自动应用运营确认结果。
