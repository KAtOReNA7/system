# M1 物理模型 v0.2 DDL 可实现性审查

| 项目 | 结论 |
|---|---|
| 审查对象 | `docs/technical-design/M1-物理数据模型-v0.2.md` |
| 数据库目标 | PostgreSQL 16+ |
| 审查日期 | 2026-06-20 |
| 总结 | **通过文档级与纯 DDL 解析可实现性审查** |
| 限制 | 未连接或创建正式数据库；未生成正式迁移文件；未执行正式数据 |

## 1. 审查方法

本轮采用三层验证：

1. 静态模型检查：解析 47 个表定义、字段语义、PK/FK/唯一/检查约束、索引、状态图和 27 项验收覆盖；
2. FK 依赖图检查：对跨表依赖执行拓扑排序，自引用 FK 单独处理；
3. PostgreSQL 语法探针：使用本地临时 `pglast 7.14` 解析 15 条非正式 DDL/事务语句，覆盖 identity、`NUMERIC(32,18)`、`UNIQUE NULLS NOT DISTINCT`、部分唯一索引、复合自 FK、带状态条件 CHECK、`num_nonnulls`、constraint trigger、advisory transaction lock 和原子状态切换。

语法探针仅存在于被 Git 忽略的临时分析目录，不是迁移文件。解析通过不能替代下一阶段在隔离 PostgreSQL 16 测试实例上的实际 `CREATE/ALTER`、触发器执行和并发事务测试。

## 2. 表数量与 v0.1 差异

修订后实际物理表数：**47**。

从 v0.1 的 42 张表变更如下：

- 删除 1 张：`income_projection_monthly_summary`。
- 新增 6 张：`issue_run`、`mapping_version_work_metric`、`mapping_version_work_form_metric`、`classification_release`、`tag_release`、`batch_impact_consumption`。
- 净增 5 张：42 - 1 + 6 = 47。
- 未合并物理表；但合并了权威语义：文件 SHA-256/大小只由指纹表维护，投影不再复制金额和月份，标准作品不再保存当前版本及首次实销缓存，影响记录不再保存单一消费者状态。

## 3. FK 与创建顺序

### 3.1 结果

- 47 张表的跨表 FK 依赖图可完成拓扑排序；不存在两个表必须互相先创建的不可解循环。
- 自引用 FK 包括任务重试、批次重导、映射基线、问题决定取代、分类父节点、月份确认取代；均可在本表创建时或建表后追加。
- `basic_info_version` 不再引用 apply batch；`basic_info_apply_batch.target_version_id` 单向引用版本，原循环已消除。
- `file_fingerprint_registry` 不再引用首个 import file；`import_file.fingerprint_id` 单向引用指纹，原循环已消除。
- `restore_point` 在批次、映射版本和基础信息版本之后创建；`basic_info_apply_batch` 和 `import_batch_undo` 在 restore point 之后创建。

### 3.2 删除策略

- 权威事实、已发布版本、问题决定和审计记录使用 `ON DELETE RESTRICT`。
- staging 与临时行可随父会话 `ON DELETE CASCADE`。
- 物理删除不承担撤销语义；批次撤销、映射退休、基础信息回滚均为状态和新版本操作。

结论：FK 可创建，顺序明确，无需通过禁用 FK 或永久保留循环空指针规避。

## 4. 主键、唯一约束与 PostgreSQL NULL 语义

### 4.1 已验证语法

- identity 主键：`bigint generated always as identity`；
- 全局单 active：`CREATE UNIQUE INDEX ... ON mapping_version ((true)) WHERE status='active'`；
- 可空列参与唯一：`UNIQUE NULLS NOT DISTINCT (...)`；
- 条件唯一：`CREATE UNIQUE INDEX ... WHERE ...`；
- 复合自 FK：分类节点父级同时引用 `id + release + system`。

以上代表语句均通过纯 PostgreSQL DDL 解析。

### 4.2 关键 NULL 修正

| 对象 | v0.2 处理 |
|---|---|
| 临时来源行 | `source_sheet_name` 可空，唯一约束使用 `NULLS NOT DISTINCT` |
| 正式收入事实来源行 | `source_sheet_name` 和七业务字段全部非空，普通 UNIQUE 不会被 NULL 绕过 |
| 分类根节点 | 兄弟节点唯一使用 `UNIQUE NULLS NOT DISTINCT`，`parent_id IS NULL` 仍参与冲突判断 |
| 月份当前确认 | `bill_month not null` + `WHERE superseded_by_id is null` 部分唯一索引 |
| active 版本 | 对常量表达式建立部分唯一索引，不依赖 nullable 业务列 |
| 问题去重 | `issue_run_id + issue_type + group_key` 全部非空 |
| 历史分册映射 | 三个业务唯一列全部非空且包含 `mapping_version_id` |

结论：关键唯一性不依赖 PostgreSQL 默认“多个 NULL 互不相等”的行为。

## 5. 完整快照映射模型

审查通过项：

- `channel_alias`、`raw_work_id_mapping`、`historical_volume_mapping` 唯一键均包含 `mapping_version_id`；
- 三张快照映射表不保存承担当前有效性语义的 `valid_from/valid_to`；
- 当前映射只由 `mapping_version.status='active'` 决定；
- 全局 active 映射版本部分唯一索引语法成立；
- `historical_volume_mapping` 使用 `historical_raw_work_id text not null`、`target_standard_work_id text not null`、`business_form text not null`；历史 ID 没有标准作品 FK；
- `income_projection` 的来源映射使用 `(source_id, mapping_version_id)` 复合 FK，不能引用其他版本的映射行。

## 6. 权威事实与冗余检查

| 事实 | 审查结果 |
|---|---|
| 文件 SHA-256、大小 | 只存 `file_fingerprint_registry`；`import_file` 不复制 |
| 原始收入金额、月份 | 只存 `income_fact`；投影通过 fact FK 读取 |
| 收入是否有效 | 不存 `income_fact.is_effective`；由批次状态 + active 映射快照决定可见性 |
| 当前基础信息版本 | 不存标准作品指针；通过 active 基础信息版本查询 |
| 首次实销/上线月 | 版本化指标表携带 `mapping_version_id` 和来源 checksum |
| 月度汇总 | M1 不持久化；使用查询视图/按需聚合 |
| 影响消费状态 | 每消费者存于 `batch_impact_consumption`，不在事件上单值覆盖 |

未发现同一权威事实由两个可独立更新的表重复维护。

## 7. 状态转换与 CHECK

### 7.1 批次

- `ready/active/revoked` 必须具备严格对账时间和 checksum；
- 金额满足 `raw - confirmed_deleted = accepted = fact = projection`；
- 行数满足 `accepted = fact = projection`；
- active/revoked 的时间字段与状态一致；
- 跨表投影覆盖由 deferred constraint trigger 在提交时检查。

### 7.2 映射与基础信息版本

- building/validated/active/retired/failed 状态与校验、激活、退休时间一致；
- 部分唯一索引保证最多一个 active；
- constraint trigger 在提交时保证恰有一个 active，并检查 active 版本完整性。

### 7.3 后台任务

- `failed` 为终态，状态图没有 `failed -> queued`；
- 单任务内瞬时重试不进入 failed；
- 新任务通过 `retry_of_task_id` 形成重试链；
- `(task_type,idempotency_key)` 唯一。

### 7.4 月份确认

- unconfirmed 不要求确认人；
- complete/incomplete 必须有确认人和确认时间。

结论：状态图与行级 CHECK 一致；需要跨表聚合的条件明确归属受控函数和 deferred constraint trigger，没有伪装成无法工作的普通 CHECK。

## 8. 批次与映射原子切换

可实现的最小事务方案：

1. 长任务在 building/validated 版本中完成事实、全量投影、首次实销指标和严格对账；
2. 短事务取得固定 mapping-switch advisory lock；
3. `FOR UPDATE` 锁定目标批次、候选映射版本和当前 active 版本；
4. 在锁内复核期望 active 版本、状态、checksum 和对账摘要；
5. 同事务 retired 旧映射、active 新映射、active/revoked 目标批次，并写恢复点、影响事件与撤销结果；
6. deferred constraint trigger 在 commit 前验证 active 投影与 active 批次集合完全一致；
7. MVCC 读者只看到提交前旧组合或提交后新组合。

部分唯一索引允许在事务内先退休旧版本再激活新版本；“至少一个 active”及投影覆盖由提交时约束触发器保证。该方案不会提交以下状态：

- 批次 active 但 active 投影不含该批次；
- 批次 revoked 但 active 投影仍含该批次；
- 两个 active 映射版本；
- 新版本只完成部分投影或部分首次实销重算。

## 9. 27 项 REQ/AT 追踪

- 当前追踪矩阵包含 27 个 M1 REQ 和 27 个 AT。
- v0.2 覆盖矩阵中的 AT 集合与权威追踪矩阵完全一致。
- 物理对象未覆盖的内容只有明确的非数据库策略，例如指定模型不可用时不降级。
- `batch_impact_consumption` 只允许 M2/M4 等消费者独立记录消费状态；未定义评估失效、自动重评、评分或阈值规则。

结论：追踪完整，未引入 M2/M4 未经确认的业务规则。

## 11. 结论与下一门槛

M1 物理数据模型 v0.2 **通过 DDL 可实现性审查**，允许进入“迁移方案与迁移文件结构设计”。

该许可不等于允许生成正式迁移文件。进入实际迁移生成前，仍应在隔离的 PostgreSQL 16 测试实例完成：

- 47 张表与全部 FK/索引的真实创建；
- deferred constraint trigger 的提交时行为；
- 两个并发切换事务的锁等待和失败回滚；
- `NUMERIC(32,18)` 对账和聚合性能；
- 192,899 行基线下的投影重建及按需月度聚合性能。
